# Authorization

Who may read and write which rows, and what the database keeps true whatever a client
sends. RBAC (roles and permissions), ABAC (per-row rules) and the integrity of the data
dictionary are enforced in PostgreSQL: by RLS policies, triggers and `SECURITY DEFINER`
functions, most of them generated by the dictionary from its metadata. This page records the
rules and their reasons. What each function, trigger and policy does is in its comment in
`apps/_core/migrations` and in `schema.md`, and the tests in `apps/test/tests` pin the rules.

A change to these rules needs the maintainer's review.

The identifiers (P1, A4, I1, D8, ...) are cited by tests and other documents and keep their
meaning.

## Premises

- **P1 · Database per tenant.** Each tenant has its own PostgreSQL database; no table carries
  a tenant or organization column. Tenant isolation is the database and connection boundary
  and is not the subject of this page: every rule here concerns authorization within one
  tenant's database.
- **P2 · An administrator sees everything.** RBAC and ABAC protect users from each other and
  refuse unauthorized access. They do not, and cannot, protect data from a database or
  infrastructure administrator, or from whoever holds a backup: policies are schema rules, a
  backup is raw data, and whoever restores it owns the instance. Data an administrator cannot
  read would need encryption in the application with keys held elsewhere, which is out of
  scope. So the audit logs, which a holder of `admin` reads and prunes, are no leak.
- **P3 · Roles.** The request role is `authenticated`, an INHERIT member of `semantius_user`.
  Every RLS policy is written `TO semantius_user` and applies to `authenticated` through the
  membership. The tables belong to a BYPASSRLS owner that is not the request role:
  `semantius_owner` when a superuser installed Semantius, else the installing role, and the
  install refuses to run without BYPASSRLS. `SECURITY DEFINER` functions run as that owner,
  without RLS.

## The canonical predicate

D8 is the heart of the model. Each entity has exactly one predicate that decides which of its
rows a caller may read:

```
access(row) = select_rule(row)                   when select_rule is set   (the rule replaces the permission)
              has_permission(view_permission)    otherwise                 (the default rule)
```

On `fields` alone, `access()` of the `entities` row of the field's entity takes the place
of `has_permission(view_permission)` (the catalog, below).

- **The rule replaces the permission.** A `select_rule` that is set is the whole read
  authorization of a row. It is not combined with `view_permission` by AND or by OR;
  `view_permission` is the predicate used when no rule is set. With a rule set,
  `view_permission` still decides, with `edit_permission` and `admin`, who sees the entity
  in the catalog (below). It is never a see-everything override.
- **Permissions are operators inside a rule.** "Support sees every ticket" is a
  `{"has_permission": "..."}` term of the rule, not the entity's `view_permission`. Grants of
  every kind (ownership, assignment, RACI, a blanket role) are OR-ed inside the one rule:
  one check expression, in which roles are terms. The rule of `modules` is an example:
  `{"or": [{"has_permission": "admin"}, {"has_permission": {"var": "view_permission"}}]}`.
  The leading terms of a rule's top-level `or` that are `has_permission` of a name written
  into the rule, like the `admin` term there, are checked once per statement in the
  generated policies, in front of the per-row rule, so a holder of one of them pays no
  per-row evaluation. The answer is the rule's own: `or` stops at the first term that
  holds. A term after any other term, or one that reads the name from the row, stays in
  the per-row rule.
- **`is_raci_actor` is a grant to the caller:** it answers whether the caller holds a role
  with the given RACI letter on the process that governs the entity and state.
  **`has_consultation` is not one:** it answers whether the record has an acted
  consultation, the same for every participant of the governing process, and false to
  everyone else. It must not be used as a per-user visibility grant.
- **A record of an `is_a` or `has_a` entity** is stored in one table per level, and only a
  caller who passes the predicate of every level reads it: each table carries its own
  entity's policies, and the entity's view is `security_invoker`.
- **The catalog follows the same model.** An entity's row in `entities`, and every row of
  that entity in `fields`, is visible to a holder of the entity's `view_permission`, its
  `edit_permission` or `admin`, and to no one else: an editor has to find the entity to
  write its records. For an `is_a` or `has_a` entity this holds on every level, because a
  record is stored on every level: its rows are visible only when its base's are, up to
  the root. `entities` says it with its own `select_rule`, which asks for the base's row
  through `set_record`. A fields row follows the `entities` row its `table_name` points
  at: the dictionary builds that rule into the policies of `fields` as one semi-join on
  `entities`, read as the caller and run once per statement, and `get_record_by_id` asks
  the same question. A row of `entity_attachables` follows both `entities` rows it names
  the same way. A user whom a `select_rule` admits to records without either
  permission reads the records and sees no metadata of the entity. Writes to the three
  tables need `admin`.
- **A rule fails closed.** A forgotten grant denies, which is the safe direction. So does a
  rule that cannot decide. A rule that raises on a row hides that row, and raises a WARNING
  once per transaction and entity that names the entity and the SQLSTATE but not the
  message, which can quote a value of the hidden row. A stored rule that is not one JsonLogic
  operation hides every row. Saving an entity refuses a rule that is not one operation
  (`90919`) or that names an operator the evaluator does not implement (`90909`), and a new
  or changed rule with an object of several keys, an argument count the operator does not
  take, a literal argument of the wrong kind or a variable that has no value where it is
  read (`90921` to `90924`). No check
  catches a rule that is true for rows it was meant to hide; the tests are what cover that.

### Where it is enforced

The one predicate is enforced identically in every access path. For a managed entity the
dictionary generates all four policies from the entity's row, and every change of
`view_permission`, `edit_permission` or `select_rule` rebuilds them, so every policy it
generates follows this table:

| Path | Rule |
|---|---|
| SELECT policy | `access(row)` |
| `get_record_by_id`, `set_record`, reference labels | `access(row)`. `get_record_by_id` evaluates it on every level the record is stored in, for a row of `fields` by asking itself for the `entities` row, and a record that fails it is answered with NULL, as a missing one is. `set_record` reads through `get_record_by_id`. The label functions are `SECURITY INVOKER`, so the referenced table's SELECT policy applies to them |
| `get_schema`, `get_schemas`, `build_schema_for_table`, `get_schema_children`, `get_module_cubes`, `get_user_cubes`, the 90238 test of `get_record_by_id` | `access(row)` of the entity's own row in `entities`, the catalog rule above (`dd_entity_viewable`, which asks `get_record_by_id`). They return no record. A caller who does not see the entity gets exactly the answer for a missing one: SQLSTATE 42P01 with `Table "<name>" not found in entities`, raised by the same statement, so no field of the error tells the two apart; the empty list from `get_schema_children`; nothing from the cubes; NULL instead of 90238. A schema names a referenced entity the caller does not see by its table name and gives nothing else from that entity's row: no labels, no key or label column, no label in the `<fk>_label` description. The extensions of a `has_a` base and the children of a parent are the ones the caller sees |
| UPDATE and DELETE `USING` | `has_permission(edit_permission) AND access(row)`: a row the caller cannot read, it cannot write. Without a `select_rule` that is the edit permission and the view permission, one check when the two are the same, or on `fields` the edit permission and the `entities` row |
| INSERT and UPDATE `WITH CHECK` | `has_permission(edit_permission)`. No rule applies to the row as it will be |
| The new row of a write that reads a column (`WHERE`, `RETURNING`) | PostgreSQL holds it to the SELECT policy as well. On an entity with a `select_rule` the row the statement is writing passes that one check, so a write may move a row out of the writer's own rule; `access(row)` applies to the row again once the statement has ended. Without a `select_rule` the check is the view permission, or on `fields` the `entities` row, and a writer that fails it is refused |

These are the rules of a managed entity. While an entity is unmanaged the dictionary does not
maintain the policies of its table. Making an entity managed adopts its table: the four
policies under the dictionary's names are dropped and recreated from the entity's row, so one
left from an earlier managed period, or written by hand under such a name, is replaced. The
table keeps any policies of other names it carried; PostgreSQL ORs permissive policies
together, so access to an adopted table can be wider than `access(row)`. That is why the flip
to managed is a decision rather than a setting, and why it is refused for the two audit logs,
whose protection is that the request role cannot insert into them or update them: it holds
only SELECT and DELETE there, under policies that admit a holder of `admin`.

## Axes

The invariants hold across every value of these eight dimensions.

- **A1 · Subject:** anonymous · signed in without the permission · view only · edit without
  view · view and edit · row owner or grantee · editor of rows it does not own · holder of
  `admin` · API key or JWT · an `is_agent` service principal · a disabled user · an OAuth
  bearer session · the request role, definer code, or a BYPASSRLS owner connection (D4).
  OAuth bearer sessions are an experimental proof of concept, not production; the rules on
  this page that name them describe that experiment.
- **A2 · Object:** a data entity with or without `select_rule`, `validation_rules` and
  `computed_fields` · a parent or child through a foreign key · an `is_a` or `has_a` family ·
  the dictionary (`entities`, `fields`) · RBAC (`users`, `roles`, `permissions`,
  `role_permissions`, `user_roles`, `user_permissions`, `permission_hierarchy`) · RACI
  (`processes`, `raci_assignments`, `process_gates`, `raci_events`) · system tables
  (`_apikeys`, `audit_record_logs`, `audit_ddl_logs`, `webhook_*`, `queues`, `modules`,
  `_settings`) · derived reads (views, `user_process_raci` among them, `search_vector`,
  cubes, `get_schema` and `build_schema_for_table`). A table named with a leading `_`
  (`_apikeys`, `_settings`) is internal and is never an entity: registering or adopting one
  is refused (`90271`).
- **A3 · Operation:** SELECT · INSERT · UPDATE · DELETE · dictionary operations (create,
  alter, drop, rename).
- **A4 · Statement shape:** reading a column · reading no column (a bare statement,
  `WHERE TRUE`, `SET c = constant`) · RETURNING · a writable CTE · `ON CONFLICT DO UPDATE`
  and `DO NOTHING` · `MERGE` · `UPDATE ... FROM` and `DELETE ... USING` · a sub-select · a
  foreign key cascade. PostgreSQL applies the SELECT policy to an UPDATE or DELETE when the
  statement reads a column, not because it is qualified. The dimension that matters is
  whether it reads a column, and the protection is the `USING` clause of the write policies,
  never the SELECT policy (I2).
- **A5 · Condition state:** `select_rule` set or empty · `validation_rules` and
  `computed_fields` present · the injected variables `$user_id`, `$old`, `$now`, `$today`,
  `$mode` · `view_permission` (reach) · `WITH CHECK`.
- **A6 · Enforcement layer:** an RLS policy (bypassed by the owner and any BYPASSRLS role) ·
  a BEFORE trigger (fires for the owner; bypassed under `session_replication_role = replica`)
  · definer logic (`/rpc/fix_id_sequence`, gated on the entity's `edit_permission` like its
  INSERT policy, and on the caller seeing the entity in the catalog, `dd_entity_viewable`)
  · PostgREST and RPC.
- **A7 · Grant path:** role to `role_permissions` · direct `user_permissions` · the recursive
  `permission_hierarchy` (it relates permissions, not roles: roles are flat) · OAuth scope
  intersection · the `is_disabled` gate · the transaction-scoped permission cache
  `app.user_permissions`.
- **A8 · Shared JsonLogic surface:** the evaluator `evaluate_json_logic` and `jl_truthy`; the
  operators `has_permission`, `is_raci_actor`, `has_consultation`, `set_record`,
  `require_permission`, `throw_error`, `value_changed`, and the comparison, logic, arithmetic
  and regular expression operators; the RPCs `/rpc/has_permission`, `/rpc/is_raci_actor`,
  `/rpc/has_consultation`, `/rpc/evaluate_json_logic`, `/rpc/get_record_by_id`,
  `/rpc/build_schema_for_table` and `/rpc/get_schema*`.

## Invariants

Each holds across all of A1-A8, except for the privileged connections D4 puts out of scope.

- **I1 · Read confinement.** No subject reads a row outside `access(row)` through any path:
  SELECT, RETURNING, a sub-select, `get_record_by_id`, `set_record`,
  `build_schema_for_table`, `get_schema_children`, a view, search, a reference label, a cube
  or an error message.
  - `get_schema_children` lists a child only for a caller who sees the child's entity in the
    catalog, and nothing under a parent the caller does not see.
  - The generated `select_rule_<entity>(row, context)` is executable by the request role, as
    a function an RLS policy calls has to be, and answers false for every row when it is
    handed no context.
  - `delete_api_key` answers a caller without `admin` who names a key of another user as it
    answers for a key that does not exist (`90402`).

  Three exceptions:
  - `RETURNING` hands a writer the row its own statement wrote, also when the write moved
    that row out of `access(row)`. The writer supplied or could already read every value in
    it. Behind PostgREST or an app server a value the client writes into the setting that
    lets that row pass opens nothing. A session that runs its own SQL, a bearer session,
    can read the secret behind that setting from `app.row_move_secret` once a write of its
    transaction has kept it there, and get past every `select_rule`. Before bearer sessions
    are enabled, the marking trigger has to read the secret from `_settings` on every row
    through the definer function and keep it in no setting, and the secret in `_settings`
    has to be replaced: it is never rotated, so a secret read once stays valid.
  - A rollup field aggregates over child rows that a reader of the parent may not see only
    when its definition carries `"include_hidden_rows": true`, the administrator's decision
    on record; without the flag such a rollup is refused (`90269`). The rule is in
    `rollup-fields.md`.
  - A table mapped to a queue puts the id of every row written to it into the queue, and a
    holder of the queue's `view_permission` reads them through `queue_read` whatever the
    entity's rules. Mapping a table to a queue is the administrator's decision.
- **I2 · No write to a row the caller cannot read.** A subject cannot UPDATE or DELETE a row
  for which `access(row)` is false, under every statement shape (A4). The `USING` clauses of
  the UPDATE and DELETE policies enforce it; nothing relies on PostgreSQL applying the SELECT
  policy to a write.
- **I3 · Write authorization.** A write requires `has_permission(edit_permission)`, and an
  UPDATE or DELETE also requires `access(row)` on the row as it is before the write. The row
  as it will be, an inserted row or the new values of an updated one, is held to the edit
  permission only, so a write may move a row out of the writer's own rule: handing a record
  to somebody else is such a write.
- **I4 · RBAC required.** No operation runs without its permission, on the indirect paths
  too: a cascade (D3), definer code, an upsert, an RPC.
- **I5 · No privilege escalation.**
  - Nobody grants themselves anything by writing `user_roles`, `role_permissions`,
    `user_permissions`, `permissions`, `permission_hierarchy` or `raci_assignments` without
    the permission that governs the table, `admin` for all six.
  - Writing `users.external_id` is escalation as well. A session is whoever's row carries the
    subject its token resolves to: the `sub` claim, `entra.<tid>.<oid>` for a Microsoft Entra
    ID token, or in an OAuth bearer session the identity PostgreSQL validated. So only a
    holder of `admin` sets or changes it (`90107`); `user:manage`, which opens `users` for
    writing, is not enough. An UPDATE that sends the value back unchanged changes nothing.
  - The system keeps an enabled holder of role 2 (Administrator), and role 2 keeps its grant
    of `admin`. Refused with 42501, `hint.code` `90104`: removing the role from its last
    enabled holder, an UPDATE that points that holder's `user_roles` row at another role or
    user, deleting or disabling that user, and deleting role 2. Refused with 42501,
    `hint.code` `90108`: removing or re-pointing the `role_permissions` row that grants
    `admin` to role 2, and deleting or renaming the permission `admin`. A statement that runs
    as a role with BYPASSRLS is exempt: a direct connection as the owner or as another role
    with the attribute, which is how a database is repaired, and definer code running as the
    owner. A superuser without BYPASSRLS is not exempt.
  - The first-user bootstrap is the one grant made without `admin`: the first principal
    created with a `last_seen`, one that has reached the system, while no user holds role 2,
    gets role 2. The election runs under an advisory lock, so two first logins cannot both
    win. A row created without `last_seen` elects nobody, and the election runs on INSERT
    only, so an existing user is never elected however often it signs in.
  - The API key of a disabled user is no credential: `validate_api_key` answers NULL for it
    and records no use. Only a holder of `admin` creates, lists or deletes the keys of
    another user.
- **I6 · Dictionary integrity.**
  - A core field is one whose `ctype` marks a column the dictionary manages, as
    `dd_ctype_is_core(ctype)` decides: `id`, `label`, `computed_label`, `audit` and `core`
    are core; the empty marker, `rollup` and `computed` are not. A core field cannot be
    deleted unless its entity is, its format and its primary key status cannot change, its
    default cannot change except the label column's, its delete mode and its referenced
    entity cannot change (`90285`, `90286`), and it cannot be renamed except the label
    column. The triggers that enforce this fire for every role.
  - Renaming the label column is a feature, not a breach: the rename carries to
    `entities.label_column` (pinned by `0460_test_ddl_rename.sql`).
  - The rename of any field, the label column included, is refused while a rule names the
    field (`90275`), when a generated name would exceed 63 bytes (`90276`), and when the new
    index name is already taken (`90274`).
  - The marker cannot be set or cleared to trap or free a field. Only a BYPASSRLS caller,
    the dictionary's own code or a migration, sets `ctype`; anybody else's INSERT has the
    `ctype` it sent discarded, and an UPDATE that changes it is refused. Of the core markers
    only the label's moves: it follows `entities.label_column`, which only a holder of the
    entities edit permission can change, and never onto a field that carries another marker
    (`90270`). The `is_core` flag `get_schema` reports is derived from `ctype`.
- **I7 · Rule completeness.** `validation_rules` and `computed_fields` run for every affected
  row on INSERT, UPDATE and DELETE, whatever the shape of the statement, with `$mode`
  (`insert`, `update` or `delete`) and `$old` (the previous row on UPDATE and DELETE, null on
  INSERT). On DELETE the rules see the row being removed: a validation rule can refuse the
  delete, and computed output is discarded. Computed fields are authoritative: a computed
  value replaces whatever the writer sent. An `is_a` or `has_a` entity runs its rules in its
  write routine, over the whole record.
- **I8 · No side channel.** `has_consultation` and `get_record_by_id` do not reveal that an
  inaccessible row exists or what it holds, and the catalog does not reveal what an entity
  the caller may not see consists of.
  - `get_schema`, `get_schemas` and `build_schema_for_table` answer an entity the caller does
    not see in the catalog exactly as they answer a missing one: 42P01 with
    `Table "<name>" not found in entities`, every field of the error the same, the context
    included. A holder of `admin` sees every entity, so for it the error means missing.
  - `has_consultation` answers false to a caller who takes no part in the governing process,
    as it answers for a record that was not consulted.
  - `get_record_by_id` reports a malformed id (`90238`) only to a caller who sees the
    entity in the catalog; anybody else gets the NULL of a missing entity.
  - Accepted residuals:
    - An `EXPLAIN` estimate shows the row count of a table the caller cannot read.
    - A foreign key violation (23503) tells a writer that a parent row it cannot read exists,
      or does not: PostgreSQL checks a foreign key past RLS.
    - A unique violation (23505) tells a writer that a key exists in a row it cannot read, on
      an entity with a `select_rule` and on one without. PostgreSQL checks a unique
      constraint over every row.

    Closing the last two would need a definer INSERT wrapper.
  - The catalog hides what an entity consists of, not that it exists. Accepted residuals:
    - PostgREST's OpenAPI root lists every table the request role holds a grant on, which
      includes every managed entity table, with its columns, types and foreign key
      relationships, and `GET /<table>` answers `200 []` for a table whose rows the caller
      cannot read where it answers 404 for a missing one.
    - The table and column comments in the PostgreSQL catalog carry the dictionary's
      labels, descriptions and enum values, and every role can read them, through
      `pg_description` and through the OpenAPI root.
    - A visible row is returned as stored, with what it says of hidden entities.
      `reference_table` holds a hidden entity's name. A rollup definition is kept whole:
      its `link_field` names the child entity and the child's link field, and its
      `value_field` and `filter` name fields of the child and the values the filter
      compares them with. The rules (`select_rule`, `validation_rules`,
      `computed_fields`, a field's `input_type_rule`) are kept whole too, and a rule that
      reads a record through `set_record` names the entity and the fields it reads.
      `get_schema` adds nothing taken from a hidden entity's row.
    - A reference property in `get_schema` keeps the JSON type and the Typed Id or Typed
      Number pattern of its own column, which follow the key type of the entity it
      references, also when that entity is hidden.
    - The rows of `modules` are not covered: a visible module row shows its
      `dashboard_config`, and its `version` moves with changes to the entities and fields
      of the module.
- **I9 · Cascade safety.** A delete cascades through `ON DELETE CASCADE` and `SET NULL`
  foreign keys whatever the deleter's rights on the children: authority to delete the parent
  governs the cascade (D3), into credential and grant children as well (D9).
- **I10 · Right layer.** Visibility is RLS plus the canonical predicate, applied again in
  every definer read path. Dictionary integrity is a trigger that fires for every role (D5).
- **I-roles · Role hygiene.** `authenticated` inherits `semantius_user`. Every policy in the
  public schema is written `TO semantius_user`, never `TO authenticated` or `TO public`. The
  request role owns no table and has no BYPASSRLS. Every view in the public schema is
  `security_invoker = true`, so it reads under the caller's RLS rather than as its owner.
- **I-perm · Permission resolution.**
  - A subject's permissions are those of its roles and its direct `user_permissions`,
    closed over `permission_hierarchy`. The hierarchy relates permissions, never roles,
    which are flat. A disabled user has none.
  - An OAuth scope list confines a session to the permissions it names and everything those
    include; it only takes permissions away, never adds one. The seeded hierarchy has
    `admin` include `public:read`, as `user:manage` includes `user:read`: `public:read` and
    `admin` are the view and edit permission an entity gets by default, and the UPDATE and
    DELETE policies of an entity without a `select_rule` check both, so a token scoped to
    `admin` alone keeps read, update and delete on the records of such an entity.
  - Outside a bearer session the permission set is computed once per transaction and kept in
    transaction-local settings, so a grant, revoke or disable committed meanwhile applies from
    the caller's next transaction, never in the middle of one while the claims are unchanged.
    The first check of a transaction builds the set, and it refuses a user who has no row
    yet rather than caching an empty set; `get_userinfo` creates the row on the first login.
  - In an OAuth bearer session (`rbac.is_bearer_session()`) the cache is not trusted and the
    context is derived again on every check, because there the client runs SQL as the
    request role and can write the `app.*` settings. Code that needs the user id outside a
    permission check has rbac derive it first (`rbac.user_id_or_null()` does both); it never
    takes a value the setting already held.
  - `users.last_seen` is a heartbeat, not a profile field. A login rewrites it at most once
    per five minutes while the claims are unchanged, and a write that changes only
    `last_seen` bumps no `updated_at` and writes no audit row.
- **I-jsonlogic · Evaluator and operators.** Each operator is correct on its own. The
  operator that reads a record, `set_record`, does so through `get_record_by_id` and so
  enforces `access(row)`, not only `view_permission`. `evaluate_json_logic` runs with the
  caller's rights and stays callable by the request role, which the operator tests need; it
  reads nothing the caller could not, so it is no way around I1. It has no limit of its own
  on the depth or the size of a rule, and only PostgreSQL's `max_stack_depth` bounds its
  recursion. That residual is accepted.

## Decisions

- **D2 · A bulk write over rows the caller cannot read filters them out silently.** That is
  what gating writes in `USING` does; no error tells the writer that such rows exist.
- **D3 · A cascade into children the deleter could not delete directly is accepted.**
  Authority over the parent governs.
- **D4 · Privileged connections are trusted and out of scope.** Regular access is
  `authenticated` through `semantius_user` and fully in scope, and so is definer logic. A
  superuser or BYPASSRLS connection reads and writes past RLS. The guards that test for
  BYPASSRLS (the last Administrator and its grant of `admin`, `external_id`, the `ctype`
  lock) let through a role that has the attribute, which a superuser need not have.
  `get_record_by_id`, and so `set_record`, reads unchecked only in a privileged direct
  session: a superuser or BYPASSRLS login with no `SET ROLE` in effect, no claims and no
  bearer identity, which can read the table anyway. That is a migration seeding records with
  computed fields. A privileged login that switched to the request role, or that carries
  claims, is checked like any request.
- **D5 · Core-field protection is a trigger that fires for every role, keyed on `ctype`.** It
  is not a JsonLogic rule, because a rule is the tenant's to edit and could be edited away.
  `ctype` is the identity of a core field; the `$mode` and DELETE arm of the record rules
  serves tenant rules, not core protection.
- **D6 · An API key carries the same authorization as its user's own token.** The key
  resolves to its user, and the token minted from it carries that user's `external_id` as its
  subject, so the database checks the session as that user. An agent is a dedicated
  `is_agent` user with permissions of its own.
- **D8 · `select_rule` replaces `view_permission`**, as the canonical predicate above states.
  The rule is the whole read authorization when it is set, `view_permission` the default when
  it is not, and permission checks are operators inside the rule. The one predicate is
  enforced identically in the SELECT policy, in the definer read helpers and in the `USING`
  clauses of the writes. No separate rule on the row as it will be exists (I3).
- **D9 · Cascades into credential and grant children are accepted.** Deleting a user removes
  its API keys and its grants, which is what deleting a user should do, and it needs
  authority to delete the user. Deleting a role that `raci_events` rows name as
  `target_role_id` is refused until those events are removed.
- **D10 · The definer read helpers apply `access(row)` themselves.** `get_record_by_id`, and
  through it `set_record`, evaluate the canonical predicate. `build_schema_for_table` and the
  other schema functions, which return no record, apply the predicate of the entity's own
  row in `entities`, and answer a caller who does not see it exactly as they answer for a
  missing entity. The read path is closed at the helpers, so
  `evaluate_json_logic` stays callable by the request role and is not revoked; I-jsonlogic
  states the residual that is accepted for it.
- **D11 · No FORCE ROW LEVEL SECURITY.** The BYPASSRLS owner is a role apart from the request
  role, and BYPASSRLS overrides FORCE, so FORCE would add nothing. The protection is the
  separation of the roles (I-roles) and the definer helpers that apply the predicate
  themselves (D10).
