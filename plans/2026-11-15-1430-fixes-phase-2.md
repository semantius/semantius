## Part A: decided

### A1. `users.external_id` can be rewritten by a `user:manage` holder

- **Defect (verified).** The `users` entity is editable with `user:manage` and
  has no validation rule (`0150_dd_bootstrap.once.sql:46`). The only trigger on
  the column is INSERT-only (`0370_raci.sql:48-51`). The caller is resolved by
  `external_id = sub` (`0080_rbac_functions.sql:612`), so moving a value onto an
  Administrator's row makes the mover's own token resolve to that row.
- **Decision.** Only a holder of `admin` may change `external_id` of an existing
  user. A direct owner or superuser connection is exempt.
- **Direction.** A `BEFORE UPDATE OF external_id ON users` trigger, SECURITY
  INVOKER with the `rolbypassrls` exemption, as `rbac.assert_administrator_remains`
  does it (`0100_rbac_rls.sql:261-278`), in the repeatable `0100_rbac_rls.sql`.
  A new 901xx code with `hint.code`, a row in `docs/error-contract.md`.
- **Check first.** The login path must not trip it:
  `rbac.upsert_user_from_jwt` (`0080_rbac_functions.sql:482-505`) does not write
  `external_id` on update (verified).

### A2. A malformed rule is accepted when saved

- **Defect (verified).** Nothing checks a rule when it is saved. In a
  `select_rule`, an unknown operator raises at read time, the generated
  predicate swallows it and every row is hidden with no error
  (`0210_computed_validation.sql:1073-1077`); an object with two keys is
  returned as data, is truthy, and every row is visible
  (`0050_jsonlogic.sql:511-512`). In a validation rule the first raises on every
  write and the second always passes.
- **Decision.** Refuse on save, for `select_rule`, `validation_rules` and
  `computed_fields`: an unknown operator anywhere, and a select or validation
  rule that is not a single operator object. `select_rule = {}` stays valid.
  A literal is not a single operator object and is refused as well, `true` and
  `false` included (decided 2026-11-15): a condition typed as text is a
  non-empty string, which is truthy, so the rule passes every record. A
  `select_rule` literal is already refused by the CHECK `select_rule_is_object`
  (23514); a validation rule literal is accepted today. A computed field may
  stay a literal, since a constant value is a legitimate result.
- **Direction.** One function that walks a rule and knows the operator list,
  called from a trigger of its own on `entities` (not from
  `build_record_logic_trigger` or `build_select_rule_policy`: Phase 1, step 3,
  case 3 stores a rule past the check and still needs the builders to work, and
  a check inside the builders would let one stored bad rule block every later
  rebuild of that entity). New 909xx codes and their rows in
  `docs/error-contract.md`.
- **To settle.**
  - The operator list exists twice then (the interpreter and the checker). A
    test must compare them; sem-schema already compares its own table against
    the `IF op = '...'` lines (`0050_jsonlogic.sql:1203-1205`).
  - Which argument positions are literal and are not walked: the name in `let`,
    the name and the entity in `set_record`.
  - An installation that already stores such a rule is refused at its next
    write of that entity, an `ensure_entities` re-apply included. Decide whether
    the upgrade reports those rules first.
  - A stored `select_rule` with two keys keeps exposing rows until it is
    rewritten. Decide whether the generated predicate should also fail closed
    for a rule that is not a single operator.

### A3. Internal tables can be adopted

- **Defect (verified).** Adoption adds the four permission policies and the

- **Decision.** Refuse registering or adopting `_settings` and `_apikeys`, and

- **To settle.** A fixed list of the two tables, or every name starting with

### A5. Fixed dollar tags in generators

- **Defect (verified).** `dd_build_record_write` wraps the generated body in
  `$RW$` (`0160_dd_functions.sql:3915-3955`) and splices a base column's
  deparsed default into it (`3841-3842`). The `default_value` CHECK does not
  forbid `$` (`0130_dd_schema.once.sql:170-175`). A default containing the tag
  ends the body early; at the least the family can no longer be built. Whether
  more is possible was not established. `dd_build_view_write` (`$VW$`, `4124`),
  `dd_build_is_a_dispatch` (`$DISPATCH$`, `4195`) and
  `rebuild_entity_label_functions` (`$body$`, `0180_managed_enable.sql:832`,
  `865`) carry only checked identifiers today, and have the same shape.
- **Decision.** No generator uses a fixed tag.
- **Direction.** Wrap all four with `dd_dollar_quote`.
- **Check first.** `dd_dollar_quote` is defined in `0210_computed_validation.sql`,
  after the files that would call it. If a label function or a family is built
  while `0180` to `0200` load, the definition has to move to an earlier
  repeatable file (an object lives in exactly one).

### A6. A `time` field is not nullable and has no default

- **Defect (verified).** `is_nullable` lists `reference`, `date` and `date-time`
  only (`0160_dd_functions.sql:674-679`), so a `time` column is `TIME NOT NULL`.
  `dd_column_default` has no zero value for `TIME` (`833-842`), so the column
  carries no default either. An insert that leaves the field out, and adding a
  required `time` field to a table that has rows, fail with a bare 23502.
  Phase 1 pins both in `0500_test_field_formats.sql`.
- **Decision.** A `time` field behaves like `date`: nullable, no default unless
  `default_value` sets one, NULL meaning "no time given". A default of `00:00:00`
  would be indistinguishable from a real midnight, which is the same reason a
  date has no zero value.
- **Direction.** Add `time` to `is_nullable`. A required `time` field then gets
  the `IS NOT NULL` check `dd_required_test` already builds for the other
  nullable formats.
- **To settle.**
  - Existing installs hold `time` columns that are `NOT NULL`. A forward
    `.once.` migration has to drop the constraint on them (loosening, so no data
    is at risk); `update_dd_field` only changes nullability when the format
    changes (`2046-2061`).
  - The sentence in AGENTS.md ("Only the formats `reference`, `date` and
    `date-time` are nullable") and the `is_nullable` comment name the list.
    AGENTS.md changes only with the maintainer's approval of the exact text.
  - Whether the Phase 1 assertions that read a `time` column's default or
    `NOT NULL` need to follow (the ones in `0500` that check the column).
- `duration`, `uuid` and `binary` are not part of this decision: see B14.

### What Phase 1 adds to Part B

- **B4, wider than reported.** Besides `infinity` and the bigint amount, a real
  date beyond year 9999 and an amount whose result leaves the timestamp range
  fail the child write too. `-infinity` and a BC date also raise 90915 (probed,
  not asserted).
- **B8, effect now run.** A table name of 62 or 63 bytes is legal but its
  `<t>_select_policy` and `<t>_insert_policy` truncate to one name (42710); 61
  bytes is the longest that builds. For `a_b`+`c` next to `a`+`b_c`: the second
  unique index is skipped silently (`CREATE UNIQUE INDEX IF NOT EXISTS`) and a
  duplicate is accepted; turning `unique_value` off, or deleting the field,
  drops the other table's index.
- **B16 (new, verified by test).** `unique_value` cannot be turned on for a
  `date`, `date-time` or `uuid` field, and a date field cannot be created with
  it: the partial index gets `AND col != ''` because `format_to_json_type` says
  "string" (`0160_dd_functions.sql:1839`, the same test in `update_dd_field`
  and in `apply_field_ddl`), and `''` cannot be cast to the column type (22007,
  22P02). `time` and `duration` very likely share it.
- **B17 (new, verified by test).** A role moved from a module to no module does
  not bump the module it left: `bump_module_version_from_related` returns when
  the new `module_id` is NULL, before the bump of the old module
  (`0420_module_version.sql:63-65`).
- **B18 (new, verified by test).** The comment at
  `0210_computed_validation.sql:1119-1120` says a write may move a row out of
  the caller's own rule. That holds only for a statement that reads no column:
  PostgreSQL also applies the SELECT policy to the new row when the statement
  has a WHERE on a column or a RETURNING, and refuses with 42501. PostgREST
  addresses a record by key, so a client always gets the refusal. Decide whether
  the comment or the behavior is right; the test asserts the comment.

### Open decisions Phase 1 collected

Recorded in the tests as "today: ..." where a test exists.

- **A2, where the check lives.** `0650` and `0600` store a malformed rule past
  the save path and assert that the builders still install it. They turn red if
  the check goes into `build_record_logic_trigger` or
  `build_select_rule_policy`.
- **A2, the stored two-key `select_rule`.** It shows every row, also when the
  entity's `view_permission` is `admin`: the select policy of an entity with a
  rule has no permission conjunct (probed). A stored unknown operator hides
  every row from everybody, an administrator included, with no error.
- **A3, how far the exposure goes.** After a managed registration with
  `view_permission = 'public:read'` a plain user reads the `_apikeys` hashes and
  the `_settings` row, because the permission policies are ORed with deny-all
  (probed; the test asserts the administrator's read). Deleting a managed
  `_apikeys` entity drops the table.
- **A1.** Whether an UPDATE that sets `external_id` to its current value is a
  change (`IS DISTINCT FROM` or `UPDATE OF`), and whether an INSERT of a user
  with a chosen `external_id` by a `user:manage` holder is covered.
- **B1.** Re-pointing the last administrator's `user_roles` row, to another
  role or to a disabled user, succeeds and leaves no enabled administrator.
  Deleting the `admin` grant of role 2 succeeds, and the guard still counts its
  members as administrators.
- **B3.** `!` over a comparison with a NULL column (`!(n>5)`: compiled 5,
  interpreted 6) and text ordering (the column's `en_US.utf8` against `"C"`).
  Also: `===` compiles as `==` with a cast; a literal is rounded to the
  column's scale; a fractional number against an integer column is refused at
  save (90265); the filter allow-list accepts `time` columns that
  `docs/rollup-fields.md` does not list.
- **`select_rule` writes.** `INSERT ... RETURNING` outside the caller's own rule
  is refused while a plain INSERT is stored (same cause as B18).
- **`label_parent`.** A hostile value is refused by `validate_label_parent`
  with 90226 before the CHECK; the CHECK answers 23514 only with that trigger
  disabled. A field that is a `label_parent` can change its format away from
  `reference` without a re-check, and the label then degrades silently.
- **B13.** A changed `precision` leaves the column's scale alone, as
  `docs/rollup-fields.md` says, while `get_schema` reports the new value.
- **`select_rule_user_bookmarks(row, NULL)`** answers true for any row (null
  equals null). Reachable only by calling the two-argument overload directly.
- **Queues.** With `queue_before_delete` bypassed, deleting a queue leaves the
  statement triggers on the mapped table and the pgmq registration behind.
- **JsonLogic, not in A4.** `{"var":"a.-1"}` returns the last element of an
  array (JavaScript: null); `{"==":[[],0]}` is false (JavaScript: true).
