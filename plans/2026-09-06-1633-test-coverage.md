# pgTAP coverage: make the number mean something, then close the real gaps

Written 2026-09-06 against the coverage run of the same day (`coverage/summary.json`,
`coverage/uncovered.md`, `coverage/lcov.info` - all gitignored, all regenerable with
`./pgdocker/pg-cli-retest.sh --coverage`). Facts below were read from that run, from
`apps/_core/migrations`, from `apps/test/tests` and `apps/nwind/tests`, and from
`packages/cli/commands/coverage.ts`. The suite passed: 86 files, 2247 assertions.

## The finding, before anything else

**The headline 63.7% function coverage is a measurement artifact, in full.** All 110
never-called functions are either vendored or generated:

- 37 are vendored pgmq (`apps/_core/migrations/0160_pgmq.sql`, pgmq v1.11.1, not ours),
- 73 are generated per entity by the data dictionary (72 `_label` / `<fk>_label`
  companions plus one `select_rule_*` compatibility overload).

**Nothing else.** The categories one would expect to find - trigger functions attributed
elsewhere, internal helpers on unreached paths, whole refusal functions never entered -
are all empty. Verified by parsing `coverage/summary.json`, not assumed.

The hand-written universe is **141 functions, 141 called - 100.0%**
(`public` 99/99, `rbac` 24/24, `audit` 11/11, `common` 7/7).

| Denominator | Called / total | % |
|---|---|---|
| As reported today | 193 / 303 | 63.7 |
| Excluding vendored pgmq | 155 / 228 | 68.0 |
| Excluding generated | 179 / 216 | 82.9 |
| **Excluding both - the hand-written universe** | **141 / 141** | **100.0** |

So there is no function-level hole to fill. **The real work is statement-level**, and the
statement figure splits the same way:

| Group | Executed / total | % |
|---|---|---|
| Ours (hand-written) | 1646 / 1851 | 88.9 |
| Generated | 82 / 95 | 86.3 |
| Vendored pgmq | 159 / 296 | 53.7 |
| Total as reported | 1887 / 2242 | 84.2 |
| **Excluding vendored pgmq** | **1728 / 1946** | **88.8** |

Of the 355 unexecuted statements, 137 are vendored and permanently unexecutable
(partman, partitioning, FIFO, grouped reads - features Semantius does not use).
**205 are ours**, and about 18 of those are out of reach in pgTAP. The remaining ~187 are
what changes 4 through 12 address.

One more thing the numbers hide, and it is the reason the generated group looks untested:
`apps/test/tests/0370_test_composed_labels.sql` is a thorough label test - it builds four
entity shapes and makes twenty-odd assertions about composition, spine re-pointing and
viewer-relative leakage. It ends in `ROLLBACK`, like every pgTAP file here, and the
universe is enumerated *after* the suite runs (`packages/cli/commands/coverage.ts`,
`universeTablesSql()` and `universeFunctionsSql()` are both called from `collect()`). The
functions it exercised no longer exist when the denominator is built, while the shipped
entities' functions sit in it uncalled. The generator itself is well covered:
`rebuild_entity_label_functions` runs 48/49 statements.

These are not inlining false negatives. The generated SQL functions carry
`SET search_path = public` (`0145_managed_enable.sql:868`,
`0180_computed_validation.sql:453`), which blocks planner inlining, so
`pg_stat_user_functions` would see them if they were called.

Sections end with a question where the answer is not mine to make. The project rule is
that nothing touching data safety, security or operability is decided by an agent alone;
changes 1, 4 and 13 are inside that rule.

## Order

1. Fix the denominator and widen `--coverage-min` (tooling; it changes what every later
   number means, so it comes first).
2. Touch the two pgmq archive tables (four lines, closes table coverage).
3. The label-generator sweep (closes function coverage on the honest denominator, and is
   a real test).
4. `validate_api_key`'s wrong-secret branch - **the one finding with a security
   consequence**.
5. through 12. The rest of the statement-level residue, in risk order.
6. Change 13: the CI ratchet.

## Change 1: fix the denominator, and let `--coverage-min` name a metric

**What is true today.** `packages/cli/commands/coverage.ts:122` declares

```
threshold: { min?: number; metric: "functions"; passed: boolean | null };
```

and `:910` sets `metric: "functions"` unconditionally. There is no way to threshold on
statements. The universe is built by `universeFunctionsSql()` (`:565`) and
`universeTablesSql()` (`:607`); in schema mode both take everything in
`public, common, rbac, audit, pgmq` minus `TEST_HELPERS` and minus extension members.
`pgmq` is in that list, so 75 of 303 functions and 296 of 2242 statements are vendored
third-party code that no Semantius test will ever reach, sitting in the denominator of
both headline ratios.

**The fix.** Two independent edits in `packages/cli/commands/coverage.ts`:

1. **Separate vendored code from ours.** Either drop `pgmq` from `CORE_SCHEMAS` for the
   coverage universe, or - better, because the queue RPCs really do depend on pgmq
   behaving - keep enumerating it and report it as its own line, with the headline ratios
   computed over the non-vendored universe. `summary.json` grows a `vendored` block beside
   `totals`; `uncovered.md` keeps its `### pgmq` section under a heading that says it is
   not counted; the console prints both.
2. **Widen the threshold metric** to `"functions" | "statements" | "core-functions"`,
   selected by the flag: `--coverage-min statements:83`. `core-functions` is the
   non-vendored, non-generated ratio - the 141/141 number. Keep the existing "percentage
   validated before any database work starts" behavior (`docs/test-coverage.md:19-21`).

**What the reported numbers become, with no test written:**

| Metric | Today | After change 1 |
|---|---|---|
| Functions | 193/303 = 63.7% | 155/228 = **68.0%** |
| Core functions | not reported | 141/141 = **100.0%** |
| Statements | 1887/2242 = 84.2% | 1728/1946 = **88.8%** |
| Tables | 42/44 = 95.5% | 42/42 = **100.0%** if the two pgmq archives leave the universe with the schema; 42/44 if they stay |

**Risk.** Low, and confined to reporting. The one trap: whichever way the pgmq *tables* are
handled must match the way its *functions* are handled, or change 2 becomes either
mandatory or impossible. If pgmq leaves the universe entirely, change 2 is moot and should
be dropped rather than done for a number nobody measures.

**Pinning test.** None in pgTAP - this is CLI code. Verify by running
`./pgdocker/pg-cli-retest.sh --coverage` and checking that `summary.json` reports the
split, then `--coverage-min statements:99` and confirming exit 1, and
`--coverage-min statements:50` and confirming exit 0.

**Done when.** `summary.json` carries a vendored/core split, `--coverage-min` accepts a
metric name, and the console prints core functions, statements and tables as three
separate ratios.

**Documentation obligation.** `docs/test-coverage.md` is permanent and this reasoning has
to survive there, written out rather than linked. Its "Reading the result" section
(`:56-80`) currently says function coverage is diluted by generated functions; it must also
say that vendored pgmq is excluded from the headline and why - it is not ours, the queue is
exercised through the RPCs in `0170_queue.sql`, and 137 of its statements are
partman/partitioning code that cannot execute here. The `--coverage-min` paragraph at
`:19-21` must document the metric argument. Copy the reasoning; do not cite this plan.

**Question for the owner.** Excluding vendored code from the headline is a judgment about
what the project claims to test. Two defensible positions: (a) pgmq is a dependency like
any other - exclude it and say so; (b) pgmq ships inside our migration and a regression in
it breaks our queue, so keep it visible in the denominator forever as a standing reminder.
I recommend (a), with the separate vendored line, because a permanently unreachable 53.7%
in the denominator makes the ratchet in change 13 unusable. **Which?**

## Change 2: the two untouched tables

**What is true today.** `coverage/summary.json` reports `pgmq.a_events` and
`pgmq.a_raci_notify` untouched - zero scans, zero writes. Both are pgmq **archive**
tables, created automatically by `pgmq.create()` (`0160_pgmq.sql:1472`, which calls
`create_non_partitioned` at `:1139`) for the two queues that ship and persist:

- `raci_notify`, inserted at `apps/_core/migrations/0210_raci.sql:1248` and provisioned by
  the queue trigger at `0170_queue.sql:74`;
- `events`, from the Northwind demo module, asserted at
  `apps/nwind/tests/0010_test_nwind_module.sql:186-210`.

Their sibling queue tables are touched (`q_raci_notify`: 8 inserts, 7 updates, 5 deletes;
`q_events`: 5 inserts, 2 updates).

Neither table is dead, and neither is unreachable. The archive *feature* is tested -
`apps/test/tests/0306_test_pgmq_operations.sql:64-69` and
`apps/test/tests/0415_test_queue_rpc_mutators.sql:41-68` both archive and read back - but
on throwaway queues (`ops_q`, `rpc_q`) whose archive tables are rolled back before the
universe is enumerated. Only the two permanent archives survive to be counted, and nothing
writes them.

**The fix.** `apps/test/tests/0350_test_raci.sql:685-686` already drains the queue with
`pgmq.delete('raci_notify', msg_id)`. Archive instead of deleting, and assert the row
landed:

```
SELECT is((SELECT count(*)::int FROM pgmq.a_raci_notify), N,
    'archived RACI notifications land in the raci_notify archive');
```

Same shape in `apps/nwind/tests/0040_test_nwind_rbac.sql`, around the
`pgmq.read('events', …)` at `:268`, for `pgmq.a_events`.

**Risk.** Very low. The only thing to watch is ordering: `0350` drains the queue so later
assertions see a known state, and archiving leaves the queue equally empty, so the existing
assertions hold.

**Pinning test.** Is the change.

**Done when.** Table coverage is 44/44 (or 42/42 - see change 1) and can be asserted at
100% in CI.

**Documentation obligation.** One sentence in each test file saying why the archive is
asserted here rather than on a throwaway queue: the permanent queues are the only ones
whose archive tables survive to be measured. That reasoning lives in the test.

## Change 3: the label-generator sweep

**What is true today.** 72 of the 73 generated never-called functions are `_label(rec <t>)`
(27) and `<fk>_label(rec <t>)` (45) companions on entities that ship - core and Northwind.
Six `_label` functions are called, all from Northwind tests: `employees`,
`employee_territories`, `order_details`, `orders`, `regions`, `territories`. Not one
`<fk>_label` companion on a shipped entity is called by anything.

`0370_test_composed_labels.sql` proves the generator on four hand-built shapes and then
rolls them away. Nothing proves the generator against the roughly 33 shapes actually
installed.

**The fix.** A new `apps/test/tests/0371_test_label_generator_sweep.sql`, about 40 lines.
A `DO` block over `SELECT table_name FROM entities WHERE managed`, calling each label
function through `EXECUTE format(...)`:

- `EXECUTE format('SELECT public._label(t) FROM public.%I t LIMIT 1', v_table)` for every
  managed entity - assert it does not raise, and that the result is non-null wherever the
  entity's `label_column` holds a non-empty value;
- for every `fields` row whose `format` is `reference` or `parent` and whose
  `reference_table` is non-empty,
  `EXECUTE format('SELECT public.%I(t) FROM public.%I t LIMIT 1', f.field_name || '_label', v_table)`
  - assert it does not raise and equals `public._label(parent)` for the referenced row.

This is not metric-chasing. It is the only test that catches "entity shape X produces a
`_label` that does not compile or that raises at runtime" - junctions, self-references and
spine chains that no hand-written fixture covers.

**Risk.** Low, but two real traps. The sweep must run as an identity that can read every
entity, or a `select_rule` policy will silently return zero rows and the assertions pass
vacuously - assert the row count first. And it must tolerate empty tables: `LIMIT 1` over
an empty table calls nothing, so count the functions actually exercised and assert that
count, otherwise the sweep can decay to zero calls without failing.

**Coverage after.** Functions **228/228 = 100.0%** on the honest denominator (266/303 =
87.8% if pgmq stays in). Statement coverage **unchanged** - label functions are
`LANGUAGE sql` and contribute no profiler statements.

**Done when.** Every managed entity's `_label` and every FK companion is called once, the
number of functions exercised is asserted rather than assumed, and function coverage on the
non-vendored denominator is 100%.

**Documentation obligation.** The test file must state, in its header comment, why it
exists and why `0370` cannot replace it: pgTAP files roll back, so entities a test creates
take their generated functions with them, and only the shipped entities are ever measured.
`docs/test-coverage.md:70-79` says "Generated label functions. One pair per entity. A
handful being called proves the generator works; calling all of them proves nothing more."
That is no longer the position and the page has to be corrected - calling all of them on
the *shipped* shapes is a generator smoke test, and it is what makes the function ratio
honest.

## Change 4: `validate_api_key` - the wrong-secret branch

**This is the one finding with a security consequence. It goes first among the
statement-level work.**

**What is true today.** `public.validate_api_key`
(`apps/_core/migrations/0110_apikeys.sql:124`) runs 14 of 17 statements. The unexecuted
three are `:143`, `:150` and - the one that matters - **`:168`**:

```
    IF v_record.secret_hash = crypt(v_secret, v_record.secret_hash) THEN
        UPDATE _apikeys SET last_used_at = CURRENT_TIMESTAMP WHERE key_id = v_key_id;
        RETURN v_record.user_id;
    ELSE
        RETURN NULL;          -- line 168, never executed
    END IF;
```

Line 168 is the credential comparison failing. The suite tests an *unknown* key id
(`validate_api_key('uk-invalid-invalidinvalidinvalidinvalid')`,
`apps/test/tests/0260_test_apikeys.sql:182`), an empty string (`:188`) and NULL (`:194`).
All three return earlier - at `:134` or at the `IF NOT FOUND` at `:159`. **No test has ever
presented a real key id with a wrong secret.**

**What a defect there would mean, plainly.** `validate_api_key` is the API-key
authentication primitive: it is `SECURITY DEFINER`, it reads `_apikeys` with the owner's
RLS bypass, and its return value *is* the authenticated user id for the whole request. If
the comparison at `:163` were inverted, or `crypt` replaced by a constant, or the `ELSE`
arm made to fall through to the success path, then **any secret would authenticate any key
id an attacker can guess or observe** - and the suite would still be green, because the
only failure mode it exercises is "key id not found". That is a full authentication bypass
behind a test suite reporting 2247 passing assertions.

**The fix.** In `apps/test/tests/0260_test_apikeys.sql`, after the existing step that
generates a real key and stashes it:

```
-- A real key id with a wrong secret must not authenticate. The other negative
-- cases in this file all return before the secret is ever compared, so without
-- this assertion the comparison itself is unexercised.
SELECT is(validate_api_key(<real key id> || '-' || repeat('0', 32)), NULL,
    'validate_api_key: a valid key id with a wrong secret does not authenticate');

SELECT is(validate_api_key('nodashatall'), NULL,
    'validate_api_key: a key with no separator is rejected');    -- pins :143
SELECT is(validate_api_key('-secretonly'), NULL,
    'validate_api_key: a key with an empty key id is rejected'); -- pins :150
```

`<real key id>` is everything up to the **last** dash (`:140`), so `split_part(k, '-', 1)`
is wrong for the `sk-seed001002-...` shape. Use the same
`substring(k FROM 1 FOR length(k) - position('-' IN reverse(k)))` split the function uses,
or read `key_id` straight out of `_apikeys`. Get this right or the assertion degrades into
another unknown-key-id case and pins nothing.

**Risk.** None to production code. The risk is writing the assertion badly and believing
line 168 is covered when it is not - check `coverage/uncovered.md` after the run and
confirm `validate_api_key` no longer appears in the partially-covered list.

**Coverage after.** +6 statements. Overall 84.4%, ex-pgmq 89.1%.

**Done when.** `public.validate_api_key` reports 17/17 statements.

**Documentation obligation.** The comment above the new assertion (quoted above) carries
the reasoning and stays with the test. `SECURITY.md` should gain a line under its API-key
material: the secret comparison in `public.validate_api_key` is pinned by a wrong-secret
assertion in `0260_test_apikeys.sql`. Name the test file, not this plan - test file paths
survive, plan filenames dangle by construction.

**Question for the owner.** This is a trust-boundary test, and its absence was not noticed
until a coverage run surfaced it. Should the same audit run over the other
`SECURITY DEFINER` authentication primitives - `rbac.uid()`, `public.get_userinfo()`,
`rbac.has_permission()` - asking specifically "is the *deny* arm executed, or only the arm
that returns before the check?" I can do that as a separate pass; it is not in this plan.
**Do you want it?**

## Change 5: `update_dd_field` - 33 unexecuted statements of DDL generation

**What is true today.** `public.update_dd_field`
(`apps/_core/migrations/0145_managed_enable.sql:360`) runs 62 of 95 statements - the worst
absolute gap we own. Unexecuted:

| Lines | What never runs |
|---|---|
| 476-488 | `ALTER TABLE … ALTER COLUMN … SET NOT NULL` / `DROP NOT NULL` |
| 494-507 | `ALTER TABLE … ALTER COLUMN … SET DEFAULT` / `DROP DEFAULT` |
| 541-544 | `ON DELETE SET NULL` and `ON DELETE CASCADE` when an FK is re-pointed |
| 566-567 | dropping the FK index when a reference field changes format |
| 621-632 | `CREATE UNIQUE INDEX` when `unique_value` is flipped **on** |
| 380, 390, 397, 401 | the four guards: `Cannot change table_name`, `Cannot change primary key status`, `Cannot change format of core system field`, `Cannot change default value of core system field` |
| 464, 538 | incompatible type change refused; `Referenced table "%" not found` |
| 420-424, 440-442, 454 | the unmanaged comment sync, the missing-column recreate, the comment-to-NULL arm |

`apps/test/tests/0220_test_unique_value.sql:79` flips `unique_value` to FALSE and asserts
the index is dropped; the ON direction is untested.

**The fix.** A new `apps/test/tests/0426_test_field_update_ddl.sql` - `0030_test_ddl.sql`
and `0425_test_default_value_hardening.sql` are both full and this deserves its own file.
Create one managed entity, then drive each field-update path and assert the catalog:

- nullable to required: `UPDATE fields SET format = 'text'` on an optional text field, then
  `is((SELECT is_nullable FROM information_schema.columns WHERE …), 'NO', …)`, and back;
- `UPDATE fields SET default_value = 'x'` then
  `like((SELECT column_default FROM information_schema.columns WHERE …), '%x%', …)`, then
  `default_value = NULL` and assert `column_default IS NULL`;
- `UPDATE fields SET unique_value = TRUE` then
  `ok(EXISTS (SELECT 1 FROM pg_indexes WHERE indexname = '<t>_<f>_unique'), …)`;
- `UPDATE fields SET reference_delete_mode = 'cascade'` then
  `is((SELECT confdeltype FROM pg_constraint WHERE conname = '<t>_<f>_fkey'), 'c', …)`, and
  `'clear'` for `'n'`;
- one `throws_ok` per guard at 380 / 390 / 397 / 401 / 464 / 538.

**Risk.** Medium, and it is the good kind: these paths build DDL by string concatenation
against user-supplied identifiers, and nothing currently proves they build valid SQL at
all. Writing the test may find real defects. Expect that, and treat a failure as a finding
rather than a bad assertion.

**Coverage after.** +28 statements, cumulative with change 4. Overall 85.6%, ex-pgmq 90.5%.

**Done when.** `public.update_dd_field` reports at least 90/95 statements; the residue is
only the unmanaged-comment arm if the file does not build an unmanaged fixture.

**Documentation obligation.** The new test's header comment states which catalog facts it
pins and why each matters. `confdeltype` in particular: it decides what a parent delete
does to children, which is a data-safety property and has to be spelled out, not implied.

## Change 6: `apply_field_ddl` - the adoption path, 53.4%

**What is true today.** `public.apply_field_ddl` (`0145_managed_enable.sql:24`) runs 31 of
58 statements - the lowest percentage of anything we wrote. It is called from exactly two
places: `enable_dd_table` (`:307`) and `update_dd_field` (`:440`), when a managed table is
missing its physical column. So it is the **adoption** path: what runs when an existing
table is brought under the dictionary. Unexecuted: the explicit `DEFAULT` clause (`:59`),
enum default resolution (`:53`), the NOT NULL fallbacks for JSON, array, timestamp and date
(`:62-77`), the FK `SET NULL` / `CASCADE` modes (`:115`, `:117`), the whole enum `CHECK`
construction (`:149-162`) and the whole partial-unique-index block (`:172-183`).

Every one of those builds DDL by concatenation.

**The fix.** Extend `apps/test/tests/0338_test_enable_managed_builds_select_rule.sql` (or
`apps/test/tests/0040_test_managed_flag.sql`, whichever the executing session judges the
better home). Build an **unmanaged** entity whose fields cover, at minimum: a required enum
with an explicit default; a `reference` field with `reference_delete_mode = 'cascade'`; a
`unique_value` text field; a required `array`. Then `UPDATE entities SET managed = TRUE`
and assert:

- `information_schema.columns.column_default` for the enum column and for the array column
  (`'[]'::jsonb`);
- `pg_constraint` holds `<t>_<f>_fkey` with `confdeltype = 'c'`;
- `pg_constraint` holds `<t>_<f>_check`, and an insert outside the enum raises
  (`throws_ok`);
- `pg_indexes` holds `<t>_<f>_unique`, and a duplicate insert raises `23505`.

**Risk.** Same as change 5, and the same instruction: a failure here is a finding.

**Coverage after.** +22 statements. Overall 86.6%, ex-pgmq 91.6%.

**Done when.** `public.apply_field_ddl` reports at least 52/58 statements.

**Documentation obligation.** In the test: why adoption is a distinct path from creation -
the dictionary re-derives DDL for columns it did not create, so its default and constraint
construction is exercised by nothing else.

## Change 7: `add_dd_field` and `delete_dd_field` - creation and teardown of column objects

**What is true today.**

`public.add_dd_field` (`apps/_core/migrations/0070_dd_functions.sql:545`) runs 58 of 77.
Unexecuted: `ALTER TABLE … DROP CONSTRAINT` plus `ADD PRIMARY KEY` when a field arrives
with `is_pk` (`:662-668`) and its `Table % already has a primary key` guard (`:652-658`);
`Referenced table "%" not found` (`:683`); the duplicate-FK notice (`:713`); the entire
insert-time unique-index block (`:767-782`); and the NOT NULL default fallbacks for array,
JSON object, timestamp and date (`:609-622`).

`public.delete_dd_field` (`:1106`) runs 15 of 23. Unexecuted `:1139-1159`: **no test ever
deletes a reference field and checks that its FK constraint and its `idx_` index went with
it**, and none deletes a `unique_value` field and checks the `_unique` index went. Orphaned
constraints block later renames and drops.

**The fix.**

- `apps/test/tests/0030_test_ddl.sql`: insert a field with `is_pk` on an entity that
  already has one, `throws_ok` on `Table % already has a primary key`; insert a reference
  field naming a nonexistent entity, `throws_ok` on `Referenced table "%" not found`.
- `apps/test/tests/0220_test_unique_value.sql`: create a field with `unique_value = TRUE`
  and assert the index exists immediately - today the file only asserts Northwind's
  pre-existing index and the drop.
- `apps/test/tests/0160_test_foreign_keys.sql`: delete a reference field, then
  `is((SELECT count(*)::int FROM pg_constraint WHERE conname = '<t>_<f>_fkey'), 0, …)` and
  the same for `pg_indexes` on `idx_<t>_<f>`; delete a unique field and assert
  `<t>_<f>_unique` is gone.
- `apps/test/tests/0425_test_default_value_hardening.sql`: a required `array` field and a
  required `date` field, asserting `column_default` is `'[]'::jsonb` and `CURRENT_DATE`.

**Risk.** Low. These are additive assertions in files that already own the feature.

**Coverage after.** +24 statements. Overall 87.7%, ex-pgmq 92.9%.

**Done when.** `add_dd_field` reports at least 72/77 and `delete_dd_field` 23/23.

**Documentation obligation.** In `0160_test_foreign_keys.sql`: leaving an FK constraint
behind after its field is deleted is what makes a later table rename fail, which is why the
teardown is asserted on the catalog rather than on behavior.

## Change 8: the generated-artifact teardown paths

**What is true today.** Two generators never have their teardown arms executed:

- `public.build_record_logic_trigger`
  (`apps/_core/migrations/0180_computed_validation.sql:29`, 39/48): `:51-53` drops
  `compute_validate_<t>` when the logic is cleared, and `:58` returns early - neither runs.
  Five refusals are also unexecuted: `:113`, `:116` (`computed_fields[%]` missing `name` /
  `jsonlogic`) and `:146`, `:149`, `:152` (`validation_rules[%]` missing `code` /
  `message` / `jsonlogic`).
- `public.build_select_rule_policy` (`:357`, 30/35): `:371-374` drops **both**
  `select_rule_<t>` overloads when the rule is cleared; `:379` returns early. Neither runs.

Leaving a stale `SECURITY DEFINER` row predicate behind after its rule is cleared is an RLS
hazard, not a cosmetic leak.

Separately: the generated **1-argument** `select_rule_<t>(p_row)` overload (`:451`,
`LANGUAGE sql`, `SECURITY DEFINER`, granted to `semantius_user`) is never called by
anything. Only the 2-argument form is, 25 times - that is the form the policies use, as
`apps/test/tests/0445_test_policy_initplan_form.sql` asserts. The 1-argument wrapper
resolves `jl_request_context()` itself and is a reachable definer entry point with zero
coverage. It is the single genuinely untested hand-reachable function in the whole universe.

**The fix.**

- `apps/test/tests/0320_test_computed_validation.sql`: after clearing `computed_fields` and
  `validation_rules`, assert `compute_validate_<t>` is gone from `pg_proc`; one
  `throws_ok` per malformed shape (five).
- `apps/test/tests/0330_test_select_rule.sql`: after `UPDATE entities SET select_rule = NULL`,
  assert **both** `select_rule_<t>` signatures are gone - count by name and assert 0, since
  counting one signature would miss the other, which is exactly the bug the teardown exists
  to prevent. And, as an authenticated non-admin:
  `is(public.select_rule_<t>(r), public.select_rule_<t>(r, public.jl_request_context()),
  'the 1-arg overload agrees with the explicit-context form')`.

**Risk.** Low to write, high value: a missed overload in the teardown leaves a definer

## Change 13: the CI ratchet

**What is true today.** `.github/workflows/test.yml:83` runs
`./pgdocker/pg-ext-retest.sh --coverage` with **no threshold**. `--coverage-min` exists and
is documented (`docs/test-coverage.md:19-21`) but nothing passes it, and it can only
threshold on functions (`packages/cli/commands/coverage.ts:122`, `:910`). **So nothing is
enforced at all right now.**

**The fix**, after change 1 has widened the metric. In `.github/workflows/test.yml:83`:

```
run: ./pgdocker/pg-ext-retest.sh --coverage-min statements:83 --coverage-min core-functions:100 --coverage-min tables:100
```

The exact flag spelling is change 1's to settle - one repeated flag or one
comma-separated argument, whichever the CLI's option parser already supports.

| Metric | Today | Threshold | Why |
|---|---|---|---|
| Statements | 84.2% (88.8% ex-pgmq) | **83** | The honest one: it says how much of the code the suite runs. One point of slack, because a threshold set exactly at today's value fails the next time someone adds a migration before its test, which trains people to lower it. More slack than that is theater. |
| Core functions | 100.0% | **100** | Non-vendored, non-generated. A meaningful invariant - "no shipped function is entirely unexercised" - that fails loudly the day someone adds an untested function. That signal is currently drowned by the 63.7%. |
| Tables | 95.5%, 100% after change 2 | **100** | It is a floor check, and a floor check parked permanently below 100 is one nobody reads. |
| **Raw function coverage** | 63.7% | **none - do not ratchet** | See below. |

**Why raw function coverage must not be ratcheted.** It is diluted by construction and it
moves for reasons that are not regressions. Adding one Northwind entity adds a `_label` and
one `<fk>_label` per FK, all of them uncalled the moment they exist, and the percentage
falls without a line of behavior changing. `docs/test-coverage.md:63-66` already says to
compare it against the previous run rather than against an absolute goal; this run proves
the point numerically - 110 never-called functions, 110 of them vendored or generated, zero
of them a gap. A gate on that number rewards writing a loop that calls generated functions
and punishes adding entities. If it stays on the console at all, print it next to the
141/141 core figure so nobody reads it as the health of the suite.

**Risk.** The ratchet fires on a red build for a reason nobody understands, and the reflex
is to lower the number. Mitigate by having the console print, on failure, which functions
lost coverage since the previous run - a follow-up, not a blocker.

**Done when.** CI fails on a coverage regression, and the three thresholds sit in
`.github/workflows/test.yml` where a reviewer sees them in the diff.

**UNVERIFIED: run-to-run determinism.** I was asked not to run the suite, so I could not
check whether two `--coverage` runs on an unchanged tree produce identical statement counts.
The one-point slack on the statements threshold is judgment, not measurement. **What would
settle it:** run `./pgdocker/pg-cli-retest.sh --coverage` twice on a clean tree without
editing anything in between and diff `totals.statements` in the two `coverage/summary.json`
files. If they are identical, tighten the threshold to 84 and drop the slack. If they vary,
the observed spread - not a guess - sets the slack, and that number belongs in
`docs/test-coverage.md`. Do this before change 13 lands, not after.

**Question for the owner.** A CI gate that can fail a release build is an operability
decision, and I should not settle any of these alone:

1. Do the thresholds fail the build, or only annotate it, for the first few weeks?
2. Do they run on both install paths, or only the extension path CI already runs?
3. Statements at 83 today - is a ratchet you raise by hand acceptable, or do you want it to
   track the previous run automatically, which is a different and larger tool change?
