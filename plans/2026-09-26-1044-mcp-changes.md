# Review: postgrest-mcp changes for entity key types

Repository: `C:\dev\postgrest-mcp`, uncommitted, on top of `8055323`.
Companion to the Semantius change that adds `entities.id_type` /
`entities.id_prefix`, 64-bit keys and the error codes 90233-90239. This file
lists every change in postgrest-mcp, what to check for each, and how to verify
it.

## Background the reviewer needs

- `entities.id_type` is one of `auto_increment` (default), `bigint`, `text`,
  `uuid`, `typeid`, `computed`. It is set when the entity is created; any later
  change is refused with `90233`. `computed` is only for system tables; a new
  entity with it is refused with `90234`.
- `entities.id_prefix` is required when `id_type` is `typeid`, and empty
  otherwise (CHECK `id_prefix_matches_id_type`). It uses the TypeID prefix
  grammar `^[a-z]([a-z_]{0,61}[a-z])?$`, must be unique among the prefixes in
  use (`unique_current_id_prefix`), and may change later.
- Dictionary metadata in Semantius: the `id_type` field row has
  `default_value = 'auto_increment'`, `input_type = 'required'` and a rule that
  makes it readonly once `created_at` is set. The column also has
  `DEFAULT 'auto_increment'`. The `id_prefix` field row is `hidden`, becoming
  `required` when `id_type` is `typeid`.
- The id field of a new entity is created by the dictionary. Its static
  `input_type` is `required` for `bigint` / `text` keys (caller-supplied) and
  `readonly` for `auto_increment`, `uuid`, `typeid` (generated).
- A record key can never change (`90236`).

### 1. `src/tools/schemas/entitySchema.ts`

- `id_type: z.enum([...six values...]).optional()`.
  - Check that it is `.optional()`, **not** `.default('auto_increment')`. The
    schema is shared by `create_entity` and `update_entity`. A zod default
    would inject `id_type` into every update, and the database refuses that
    for every entity whose key type is not `auto_increment` (90233). When the
    key is omitted on create, the database default applies. This is the same
    convention as `edit_mode` and `entity_type`: no schema in
    `src/tools/schemas` uses `.default()`.
  - Check that `computed` is in the enum. It is a value of the column, and
    `deno task check-schema` compares the enum against the dictionary, so
    leaving it out is reported as drift. The description states that a new
    entity using it is refused.
- `id_prefix: z.string().optional()`. There is no regex in zod: the database
  CHECK is the authority, and its error names the constraint.
- Descriptions: check that they agree with the Background section above.

### 2. `src/SKILL.md` and `src/generated/instructions.ts`

  - they recommend leaving it unset (`auto_increment`) in the normal case;
  - they tell the agent never to use `computed`;
  - they say `id_prefix` is required with `typeid`.
- The `id` bullet under "The system automatically creates these fields" names

- The high-risk list mentions that `id_type` and key values cannot change

- Format table: the `reference` / `parent` rows no longer say "(INTEGER)".
- Check that `instructions.ts` is exactly what `deno task generate` produces
  (step 2 of Verification). The same task also rewrote
  `src/generated/plugin.ts`, and git shows no change there.

### 3. `src/db/hook.ts`

- Only `export` is added to `filterWebhookData`, plus the doc comment.
- The behavior is deliberately unchanged. The import drops fields whose
  static `input_type` is `readonly`, so:
  - `bigint` / `text` keys (`required`) are kept;
  - `auto_increment`, `uuid` and `typeid` keys are dropped and generated by
    the database.

  Check that this is the wanted behavior for webhook imports of `uuid` /
  `typeid` entities: a sender cannot set its own uuid or TypeID through the
  webhook, even though the database would accept one.
- The export exists only for the test. Check that exporting it is acceptable.

1. `deno task test` should report 37 passed and 0 failed (34 before, plus the 3
   new tests).
2. `deno task generate`, then `git diff --stat src/generated`. This should show

   `../semantius/schema.md`, which must be the regenerated one from the
   Semantius change (it contains the `id_type` / `id_prefix` rows). The

   `id_type` and `id_prefix`, whose tool descriptions are written for agents.

   `TS2345 ... Uint8Array ... BodyInit` at `src/index.ts:188`. That error

5. The end-to-end check is not done yet. It needs this postgrest-mcp and the
   Semantius migrations deployed together. Then, through the MCP tools:
   - `create_entity` with `id_type: "typeid"`, `id_prefix: "acct"`;
   - insert a record without an id, and check that the returned id looks like
     `acct_01...`;
   - PATCH the id, and check that it is refused with 90236;
   - `update_entity` changing `id_type`, and check that it is refused with
     90233;
   - read the schema, and check that the id is `type: string` with a TypeID
     `pattern`;
   - `update_entity` without `id_type` on that entity, and check that it
     succeeds. This proves the missing zod default matters.
