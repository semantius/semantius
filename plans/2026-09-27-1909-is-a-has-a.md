# Plan: `is_a` and `has_a` entity key types

## Context

So far every Semantius entity is one flat table. Business models also need records
shared between entities.

- **is_a (subtypes).** Examples:
  - `activities` > `emails` > `classified_emails`, and `tasks` is_a `activities`
  - `persons` / `organizations` is_a `business_partners`
  - the user's invoices / payments is_a journal_entries

  Every record is exactly one type. All parts share the key minted by the entity it
  was created through, so `activities` holds `act_…`, `eml_…`, `cle_…` and `tsk_…` ids.
- **has_a (extensions).** `customers` / `suppliers` has_a `business_partners`.
  - A partner has 0..1 customer and 0..1 supplier record.
  - The base key (`bp_…`) is used everywhere. One level only.

Both are new `entities.id_type` values; the base is named in the new
`entities.id_refentity`:
- has_a needs a `typeid` base;
- is_a needs a `typeid` or `is_a` base.

The entity name becomes a view that joins the base chain with a physical `<t>_ext`
table, written by an INSTEAD OF trigger. get_schema returns base fields first. A has_a
base lists its `extensions[]`. Full-text search spans all levels. postgrest-mcp's
SKILL.md and tools follow.

Reviewed four times:
- a design stress test against the code
- 3NF / S/4HANA / Microsoft CDM fitness
- DRY/KISS
- a readiness review that checked every claim against the migrations, the tests,
  `docs/error-contract.md`, `RELEASE.md` and postgrest-mcp

The findings are included.

## Decisions (with the user)

- **Permissions: base + extension.**
  - Each physical table keeps only its own entity's RLS policies.
  - The view is `security_invoker` and writes run as the caller, so RLS governs every part.
  - Can be widened later.
- **is_a writes are polymorphic (option C).**
  - A write through a supertype view or the root table is carried down to the record's
    own type.
  - Example: `DELETE /activities?id=eq.cle_01` checks the delete permission of all
    three parts and runs the delete rules of `classified_emails`, then `emails`. It then
    deletes the classified_emails part, the emails part and the activities row.
  - Updates run the rules of every level below the change.
  - The type is read from the id prefix, which is fixed for is_a entities.
- **Deletes never cascade into parts.** Every `_ext` foreign key is `ON DELETE RESTRICT`.
  - Parts are deleted explicitly, bottom-up, needing every part's permission.
  - A has_a base record that still has extensions cannot be deleted. Its extensions are
    removed first, through their entities.
- **A reference field of an is_a subtype cannot use `cascade`** (90249, feature
  `cascade`).
  - An RI action runs inside a trigger, where the `_ext` guard lets writes through,
    so a cascade would delete one part and leave the rest of the record behind.
  - has_a extensions may cascade: that only detaches the extension.
- **An is_a/has_a entity that still has records cannot be deleted.**
  - This also refuses a module delete while one of the module's family entities has
    records. Plain entities in a module are dropped with their data; families are not.
- **The suffix is `_ext`.** Entity names ending in `_ext` are reserved by
  `valid_table_name`.
- **v0.5.0-beta1 is the highest release and still mutable** (`RELEASE.md`: the highest
  version may be regenerated and re-released; 6deb66e edited 0150 in place the same
  way).
  - `0130`/`0150` are edited in place. Databases that already installed beta1 do not
    receive the change, which `RELEASE.md` accepts for a re-release.
  - No new migration or test files: new SQL goes into existing migrations, and new
    tests become parts of existing test files.
- **Error codes start at 90240** (the enum commit `6deb66e` uses none).
  - Every refusal this design causes carries a catalog code, per `docs/error-contract.md`.
  - Native errors are used only where the contract covers them (FK, CHECK and unique
    constraints, localized by constraint name).
- **is_a prefixes are fixed at creation.** typeid roots may still change theirs; the
  root's `typeid_assign` is then reinstalled with the descendant prefixes.
- **The generated write routines live in `common`**, which PostgREST does not expose,
  so they are not RPC endpoints.
  - `record_write_*` and `record_rules_*` are called from trigger bodies, which run as
    the caller, so `semantius_user` gets EXECUTE on them.
  - The trigger functions (`view_write_*`, `is_a_dispatch_*`) need no grant:
    PostgreSQL checks EXECUTE on a trigger function when the trigger is created, not
    when it fires.

## Design

### 1. Metadata (0130/0150, in place)

- **Column:** `id_refentity TEXT REFERENCES entities(table_name) ON DELETE RESTRICT ON UPDATE CASCADE`,
  after `id_prefix`, plus the index `idx_entities_id_refentity`.
- **CHECK constraints:**
  - `valid_id_type` adds `is_a` and `has_a`.
  - `id_prefix_matches_id_type` becomes `(id_type IN ('typeid','is_a')) = (id_prefix <> '')`.
  - New `id_refentity_matches_id_type`: `(id_type IN ('is_a','has_a')) = (id_refentity IS NOT NULL)`.
  - New `derived_entity_managed`: `id_type NOT IN ('is_a','has_a') OR managed`.
  - `valid_table_name` additionally requires `table_name !~ '_ext$'`.
- **Field rows:**
  - `id_type` gets the new enum values and descriptions.
  - The `id_prefix` rule becomes `required` for typeid and is_a.
  - New `id_refentity` row:
    - format `reference` to `entities`, ctype `core`, field_order 103, title "Base Entity";
    - `hidden` unless id_type is is_a/has_a, then required on create and readonly after.
- **Platform validation rule** (like 90233): an is_a entity's `id_prefix` cannot change (90245).
- **A base cannot become unmanaged** while entities are based on it (90252).
  - `managed` can otherwise flip from true to false freely.
  - The CHECK covers only the derived entities themselves.

### 2. Storage and naming

- **View `public.<t>`:**
  - `WITH (security_invoker = true)`.
  - Columns: `e.id`, then the family fields root first, `e.created_at`,
    `GREATEST(<levels>.updated_at)`, and the concatenated `search_vector` of the levels
    that have one.
  - Joined `ON` the key. `e.id` comes from `<t>_ext`, so PostgREST gets the primary key
    and links references to the view.
  - Column defaults are copied from the physical columns.
- **Table `public.<t>_ext`:**
  - Columns: `id common.typeid PRIMARY KEY REFERENCES <parent>(id) ON DELETE RESTRICT`,
    the own fields, `created_at`, `updated_at`. No label column.
  - `<parent>` is the base table for has_a, and the direct parent's physical relation
    for is_a.
  - Standard grants, RLS and the entity's four policies.
  - Created without `IF NOT EXISTS`. A clash raises 90250.
- **One column source.** `dd_family_fields(t)` (own fields plus inherited ones, root
  first) feeds the view, the write routines and get_schema. Families are always managed
  (CHECK), so every fields row has its column.
- **Naming.**
  - Objects on a physical table are named after it (`<t>_ext_<f>_fkey`,
    `<t>_ext_select_policy`, …).
  - Entity-level functions keep the entity name:
    - in `public`, as today: `select_rule_<t>` and `_label(<t>)`;
    - in `common`: `record_rules_<t>`, `record_write_<t>`, `view_write_<t>` and
      `is_a_dispatch_<root>`.
- **`dd_relation(table_name[, id_type])`** gives the physical relation. It is resolved
  once per function, only where a family can occur:
  - 0160:
    - policies, `create_dd_table`, `delete_dd_table`, `update_entity_policies`
    - field DDL (FK targets via `dd_relation(reference_table)`) and comments
    - `update_search_vector_column`, `dd_sync_typeid_prefix`
  - 0170: rename
  - 0200: audit
  - 0210: generators
  - 0180: labels

  Not used in `enable_dd_table`/`apply_field_ddl` (families are never unmanaged) or in
  `field_data_type` (the view's `pg_attribute` suffices).
- **A missed conversion is not always loud.**
  - A view refuses ADD/DROP COLUMN, CREATE INDEX, ADD CONSTRAINT and row triggers,
    so a miss there fails at once.
  - But RENAME COLUMN, SET/DROP DEFAULT, COMMENT ON COLUMN and GRANT succeed on a
    view. The refresh then copies the stale physical value back onto it.
  - The tests therefore assert these on `<t>_ext`, not only on the view.

### 3. Writes

All routines are generated per entity in `common`: static SQL, pinned `search_path`,
COMMENT, EXECUTE revoked from PUBLIC. `record_write_*` is SECURITY INVOKER.
`record_rules_*` is SECURITY DEFINER. Both are granted to `semantius_user`.

- **`record_rules_<t>(p_mode, p_old jsonb, p_data jsonb) RETURNS jsonb`** holds one
  entity's computed fields and validation rules. It returns the data with the computed
  values applied.
  - **SECURITY DEFINER, like today's trigger.** The rule block calls
    `jl_error_hint`, which the request role cannot execute. Under invoker rights, a
    failing rule would surface as 42501 instead of its own code.
  - **Generated by `build_record_logic_trigger`** for every managed entity with rules.
    `compute_validate_<t>` becomes a thin trigger wrapper: it builds the data from
    NEW or OLD, calls the function, and writes the result back into NEW.
  - Hints name the owning entity, because the function carries it rather than
    reading `TG_TABLE_NAME`.
  - This is the one source of the rule logic. The generator is monolithic today, and
    its emitted text depends on `TG_TABLE_NAME`, `TG_OP`, `OLD` and `NEW`, so a shared
    SQL-text helper would not work.
- **`record_write_<t>(op, old, new, from_root)`** is the one routine that writes a
  record whose own type is `t`. Every entry point calls it.
  - **Rules.**
    - It chains `record_rules_<level>` for the derived levels it writes, inherited
      levels first, over the whole record: NEW, a full `$old` and `$mode`.
    - Computed fields may set any column of the record.
    - The root's own rules stay a BEFORE trigger on the root table and run after the
      derived rules (they validate the final root row).
    - `_ext` tables have no rule trigger.
  - **INSERT, is_a.**
    - The id is `typeid_generate_text(<own prefix>)`; a supplied id must carry it (90237).
    - Inserts the root, then each `_ext` level top-down.
    - An existing id fails with 23505: the type is fixed at creation.
  - **INSERT, has_a.**
    - No id, or an id no visible base row has: insert the base, then `<t>_ext`.
    - A supplied id must then carry the base's own prefix (90237). The root's
      `typeid_assign` accepts descendant prefixes from inside a trigger, so without
      this check a has_a on an is_a root could create a subtype root row without its
      parts.
    - The id of an existing, visible base row: **attach**. Only `<t>_ext` is inserted.
      A supplied base value that differs from both the stored value and the default
      raises 90246.
  - **UPDATE.**
    - Writes the levels from the highest level whose columns changed down to `t`, and
      always `t`; their rules run.
    - Which levels changed is decided after the rules ran, since computed fields may
      set any column.
    - Levels above the change are untouched.
    - A changed key raises 90236.
  - **DELETE.**
    - **is_a:** runs the delete rules of every derived level on the whole record. It
      then deletes bottom-up: `t`, …, the first derived level, then the root.
    - **has_a:** runs the delete rules of `t` and deletes only `<t>_ext` (detach). The
      base record stays and is deleted through its own entity.
  - **Permissions without half-writes (authz D2).**
    - UPDATE and DELETE first lock every level they will write, top-down, with
      `SELECT … FOR UPDATE`. That applies the UPDATE policies, whose predicate here
      equals the DELETE policies' (`edit_permission`, AND `select_rule_<t>` when one
      is set).
    - If a level is not lockable, the routine returns NULL and the record is skipped
      like any RLS-filtered row.
    - Top-down locking also rules out deadlocks.
    - A refused INSERT raises 42501.
  - **`from_root`.** Set when called from the root's own trigger. The root row is then
    locked and written by the outer statement; the routine returns the root column
    values for it.
  - **Result.** Returns the stored record, re-read through the view. If the caller
    cannot read it, the input record is returned.
- **`view_write_<e>()`** is the INSTEAD OF INSERT OR UPDATE OR DELETE trigger on each
  derived view.
  - INSERT calls `record_write_<e>`.
  - UPDATE/DELETE find the record's own type `t` from its prefix: `e` or a descendant
    of `e`, via a generated `CASE`.
  - It then loads the full `t` row, overlays NEW's `e` columns, calls
    `record_write_<t>`, and returns the `e` projection.
  - Example: `PATCH /emails` on a `cle_` record runs the `classified_emails` rules.
- **`is_a_dispatch_<root>()`** is a BEFORE UPDATE OR DELETE trigger on every is_a root.
  - It acts only at `pg_trigger_depth() = 1` (a direct write) and only for a subtype
    prefix. A plain root row costs one `CASE`.
  - It loads the full record, overlays NEW's root columns, and calls
    `record_write_<t>(…, from_root => true)`.
  - It returns NEW with the resulting root columns, or NULL if the record is skipped.
  - Its name sorts before `compute_validate_trigger` (e.g. `a_is_a_dispatch`).
  - So `PATCH`/`DELETE /activities` works on every record, including bulk statements.
- **One builder for both dispatchers.** `view_write_<e>` and `is_a_dispatch_<root>`
  do the same work: prefix to `t`, load the full `t` row, overlay, call
  `record_write_<t>`. They differ only in `from_root` and the projection they return,
  so one builder generates both.
- **Upserts are not possible** on these views (ON CONFLICT, PostgREST merge-duplicates
  and PUT fail with 42P10, at plan time). A test pins this and the docs say so.

### 4. Keys and guards (0045, 0160)

- **Key types.**
  - `dd_id_type_data_type`: is_a/has_a map to `COMMON.TYPEID`.
  - `dd_id_column_ddl` gets an `_ext` branch that adds the FK to the parent.
  - Id field format `string`: readonly for is_a; for has_a
    `{"if":[{"var":"id"},"readonly","default"]}`.
- **Subtype prefixes on the root.**
  - The is_a root's `typeid_assign` gets its own prefix plus its descendants' (fixed)
    prefixes as trigger arguments.
  - It accepts a descendant prefix only at `pg_trigger_depth() > 1`, i.e. from
    `record_write`. A direct insert cannot create a half subtype record (90237).
  - One installer, `dd_install_id_triggers`, computes that list, and every path that
    installs the trigger calls it: `create_dd_table`, `dd_sync_typeid_prefix` (a root
    prefix change) and the family refresh.
  - `dd_sync_typeid_prefix` today recreates the trigger with the root's prefix only.
    That would break every subtype insert after a root prefix change.
- **`common.ext_write_guard()`** on every `_ext` table: BEFORE INSERT OR UPDATE OR DELETE.
  - It refuses at `pg_trigger_depth() < 2` (90244): only the write routines write `_ext`.
  - It names the entity as `left(TG_TABLE_NAME, -4)`, which is unambiguous because
    `_ext` is reserved.
- **has_a base guard.** A BEFORE DELETE trigger on every has_a base refuses to delete a
  record that still has extension rows (90251). The FK RESTRICT is the backstop.
- **The depth invariant, stated once and repeated in the comment at every depth check.**
  - Inside a trigger, only `record_write_*` and RI actions write an `_ext` table or
    insert into a typeid root.
  - `record_write_*` checks the prefix of every id it inserts.
  - RI actions are limited to what cannot split a record: an is_a subtype field
    cannot `cascade` (90249).
  - A SET NULL on an `_ext` column runs without the derived rules, since `_ext` has no
    rule trigger.
  - A cascade or SET NULL into an is_a root reaches only the root row. A subtype
    record's delete fails on `<t>_ext_id_fkey`, and a SET NULL skips the subtype rules.
  - AGENTS.md tells module authors that their own triggers must not write family
    tables.
- **Installation.** The root's `typeid_assign` (through `dd_install_id_triggers`),
  `is_a_dispatch_<root>` and the has_a base guard are (re)installed by the family
  refresh.

### 5. Row rules and labels

- **`select_rule`.**
  - For derived entities the functions take the `_ext` row type and merge the parent's
    row (`public.<id_refentity>`, read as SECURITY DEFINER) under the own row, so the
    rule sees the whole record.
  - Policies go on `_ext`.
- **`get_record_by_id`** checks every level's canonical predicate, the same result the
  invoker view gives under RLS.
- **Labels.**
  - A derived entity's `label_column` is the base's and `label_parent` is empty. Both
    are set on insert; changing them raises 90242.
  - A base label-field rename propagates to the descendants, as one extra WHERE
    condition in `validate_field_rename_and_format`.
  - `_label(<view>)` is the parent's composed label.
  - `<fk>_label(<view>)` is generated for the family's reference fields.
  - Both come from `rebuild_entity_label_functions`, which the refresh calls. There is
    no second label generator.

### 6. get_schema (0250)

- A helper over `dd_family_fields` builds `properties` and `required`.
- **Derived entities:**
  - root first, then each level, then the entity's own fields;
  - the ancestors' id and audit fields are replaced by the entity's own;
  - inherited properties carry `"inherited_from": "<entity>"`;
  - the TypeID `pattern` applies to is_a/has_a keys and to references to them.
- **Access:** `dd_entity_viewable(t)` requires the view permission of every level. It
  drives the schema gates, `get_record_by_id` and the `extensions[]` filter.
- **has_a bases** get `extensions: [{table, properties, required}]`. **is_a bases** get
  nothing extra.

### 7. Full-text search

- Each table keeps its own generated `search_vector`, and the view concatenates them.
- `wfts` on `customers` matches partner and customer fields. It cannot use the GIN
  indexes; this is documented.
- **One predicate.** `searchable` has a single predicate, a function over family
  fields.
  - Today the expression is repeated in `update_table_searchable_flag`,
    `enforce_table_searchable_consistency` and `enable_dd_table` (0180). All three
    call the function.
  - The copy in `0240_dd_bootstrap_complete.once.sql` is history and stays.
- A change to a base's searchable fields also recomputes its descendants' flags.

### 8. Lifecycle

- **One refresh entry point.** `dd_refresh_family(p_touched)` runs at the end of the
  existing `apply_field_searchable_change`. That helper is called by the three
  statement-level `fields` triggers, after all row-level DDL, with the touched tables
  taken from their transition tables.
  - For every family containing a touched table it rebuilds:
    1. the views (DROP VIEW CASCADE, CREATE, defaults, comments, grants)
    2. all `record_write_*` / `view_write_*` functions and triggers
    3. the root's `typeid_assign` (through `dd_install_id_triggers`) and `is_a_dispatch`
    4. the has_a base guard
    5. `_label` / `<fk>_label` (through `rebuild_entity_label_functions`)
  - It is read-only and exits at once when no family is touched, so 0820's cost test
    stays green. 0820 counts audit rows, so any write to `entities` on the non-family
    path would break it.
- **`search_vector` rebuilds.** `update_search_vector_column` drops `search_vector`
  with `CASCADE`, and the same refresh restores the views.
  - Today both of its drops (0160:1766-1769, 1830-1833) have no CASCADE.
  - Without it, the first searchable change on a family table would fail with 2BP01,
    because a view depends on the column.
- **Create:** `create_dd_table` builds `<t>_ext` and its guard. Inserting its field rows
  triggers the refresh, so the view exists before the `zzz_label_fn_*` triggers fire.
- **Rules change:** `manage_record_logic_trigger` rebuilds `record_rules_<t>`. On a
  derived entity it also refreshes the family, because whether that function exists
  changes what `record_write` calls.
- **Managed:** a base with dependents cannot become unmanaged (90252).
- **Rename:**
  - `rename_dd_table` renames `<old>_ext` and its objects, renames the view with
    `ALTER VIEW`, and drops the old-named functions.
  - An AFTER trigger on entities refreshes the family.
  - `id_refentity` follows through `ON UPDATE CASCADE`. The write-once check (90241)
    allows exactly the case where `OLD.id_refentity` no longer exists and
    `NEW.id_refentity` does.
- **Delete, checked at the top of `delete_dd_table` before any DDL:**
  - A family entity with records raises 90247. This also applies inside a module-delete
    cascade.
  - A base entity others are based on raises 90248. Dependents whose module row is
    already gone, as in a module-delete cascade, do not count; the FK is the backstop.
  - Otherwise the view, functions and `<t>_ext` are dropped (`IF EXISTS`) and the family
    is refreshed.
- **Trigger names are chosen for order:**
  - The entity check trigger sorts before `set_entity_defaults_trigger`.
  - The field-collision trigger sorts before `validate_field_rename_and_format_trigger`.
  - `ext_write_guard` and `is_a_dispatch` sort before `compute_validate_trigger`.

### 9. Error codes (902xx) and constraints

| Code | Meaning |
|---|---|
| 90240 | Entity `${table}` cannot be based on `${base}` (wrong id_type, itself, or unmanaged; the hint states the rules) |
| 90241 | `id_refentity` is set when an entity is created and cannot be changed |
| 90242 | `label_column` and `label_parent` of `${table}` come from its base `${base}` |
| 90243 | Field `${field_name}` of `${table}` collides with `${other}`, which shares its records (ancestors and descendants only; id and audit names excepted) |
| 90244 | `${relation}` stores part of `${table}` records; write them through `${table}` |
| 90245 | `id_prefix` of an is_a entity is set when it is created (platform rule) |
| 90246 | Attaching `${table}` to `${base}` record `${id}`: `${field}` differs from the stored value; change it through `${base}` |
| 90247 | Entity `${table}` still has records; delete them first |
| 90248 | Entity `${table}` cannot be deleted while `${dependents}` are based on it |
| 90249 | `${feature}` is not available for `${id_type}` entity `${table}` (`feature` is an identifier: `order_column`, `queue_table_events`, `process_gates`, `cascade`) |
| 90250 | Table name `${relation}` is already in use |
| 90251 | Record `${id}` of `${table}` still has a `${extension}` record; remove it through `${extension}` first |
| 90252 | Entity `${table}` cannot become unmanaged while `${dependents}` are based on it |

- 90236 and 90237 are reused, naming the entity.
- Constraint names to add to `docs/error-contract.md`:
  - `id_refentity_matches_id_type`, `derived_entity_managed` and
    `entities_id_refentity_fkey`
  - `<t>_ext_id_fkey`: the record still has a `<t>` part; delete it through `<t>`.
    This is what a cascade into an is_a root hits.
  - the updated meanings of `valid_id_type`, `id_prefix_matches_id_type` and
    `valid_table_name`
- The only native errors left, both documented: 42P10 for upserts (raised before any
  trigger runs) and PostgreSQL's identifier truncation (an existing, general issue).

### 10. Limitations (documented, not built)

- **Refused with 90249:**
  - queue mappings (0340), RACI gates (0370) and `order_column` (0230) on a derived
    entity. A base's own order column is not a field and stays out of the views.
  - `cascade` on a reference field of an is_a subtype.
- **RI actions into an is_a root** reach only the root row. For a subtype record, a
  cascade fails on `<t>_ext_id_fkey`, and a SET NULL skips the subtype rules.
- **Module delete** is refused while a family entity has records (90247).
- **Upsert** is unavailable on derived entities; the webhook import works around it.
- **Search** across levels is not index-backed.
- **Audit** is per physical table (`emails_ext`, `activities`); a part is logged only
  if its own entity is audited.
- **Performance:** a supertype write of a subtype record does more work (loads the
  record, runs the subtype rules, writes its parts).
- **Deferred:**
  - kysely/drizzle generation for derived entities (the committed examples are still
    regenerated for the new column);
  - `ensure_entities` ordering of is_a records;
  - a name-length guard;
  - references to several unrelated entities, abstract bases, composite uniqueness.

## Implementation steps

1. **0130/0150** in place: column, CHECKs, index, field rows, platform rule.
2. **0045:** `typeid_assign` takes the descendant prefixes as arguments and accepts
   them by depth; `common.ext_write_guard`.
3. **Top of 0160**, SQL functions before `field_data_type`: `dd_relation` (both),
   `dd_ancestors`, `dd_descendants`, `dd_family_fields`, `dd_entity_viewable`, the
   searchable predicate function. Then the §2 `dd_relation` conversions and the
   searchable-predicate call sites.
4. **0210:** split `build_record_logic_trigger` into `record_rules_<t>` and the thin
   `compute_validate_<t>` wrapper.

   **Checkpoint 1: the full suite passes unchanged.**
5. **0160 family machinery, without polymorphism:**
   - the entity check trigger (90240–90242, 90252, id/label inheritance)
   - the field checks: collisions (90243) and `cascade` on an is_a subtype (90249)
   - the `delete_dd_table` checks (90247/90248)
   - the `create_dd_table` derived branch
   - `dd_install_id_triggers` with descendant prefixes, also called from
     `dd_sync_typeid_prefix`
   - `dd_refresh_family` generating:
     - the views
     - `record_write_*`, and `view_write_*` for own-type records
     - the has_a guard (90251)
   - `CASCADE` in `update_search_vector_column`
   - the rename AFTER trigger
   - `COMMENT ON VIEW` in `update_dd_table_comment`
   - `get_record_by_id`
6. **0210** (the select_rule merge), **0170** (rename, label propagation), **0180**
