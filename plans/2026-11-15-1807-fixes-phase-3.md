### The injection audit (S1)

**This is the first work of Part 1, before any other test is written.** The
maintainer asked for SQL injection tests when Phase 1 was planned. What Phase
1 delivered is narrower than that, and nobody said so until the maintainer
asked three times.

What exists today, all from Phase 1 step 7:

- `0535_test_identifier_hardening.sql`: twelve hostile values, a `CREATE ROLE`
  payload among them, against six name columns (`entities.table_name`,
  `id_column`, `label_column`, `label_parent`, `order_column`,
  `fields.field_name`), on insert and on rename; quotes, percent, dollar and
  backslash in enum values, `title`, `description` and the two labels; a
  dollar tag in a column default.
- `0530_test_default_value_hardening.sql`: `default_value`, and a dollar tag
  in a rule, a validation message and a select rule.
- `0910_test_no_unsafe_functions.sql`: no generator writes a fixed dollar tag.

What has no hostile-input test, as far as those files say. Whether each is
safe is what this audit establishes; none is known to be open: permission
names in generated policies, `id_prefix` in the TypeID trigger arguments, the
`code` of a validation rule and the name of a computed field in the generated
trigger, `reference_table`, queue names, the names in a rollup definition,
module and role names, and every value that reaches the generators listed
under point 5.

Phases 1 and 2 fed hostile names and hostile text into the dictionary's entry
points and showed that they are refused or stored as text. Nobody read the
statements themselves, so the suite shows that the tried inputs are safe, not
that every statement is. One class was found that way and fixed in Phase 2 (a
fixed dollar tag around a generated function body). This step reads them all.

1. List every place in `apps/_core/migrations/*.sql` that executes SQL built
   at run time: `EXECUTE` of anything but a constant, and every generator that
   writes a function body, a policy, a trigger, a view or a constraint. The
   word `EXECUTE` also occurs in every `GRANT EXECUTE` and `REVOKE EXECUTE`;
   those are not statements to audit.
2. For each place, list every value spliced into the text and how it gets
   there: `%I` or `quote_ident`, `%L` or `quote_literal`, a fixed allow-list, a
   value read from the catalog (`format_type`, `pg_get_expr`, `regclass`), or
   raw (`%s`, `||`) from a column a caller can write.
3. Write the result into `docs/` as a permanent page (one table: file,
   function, value, source of the value, how it is quoted, test that pins it).
   A value from a writable column that reaches the text raw, or through a
   quoting that does not cover its context (a dollar tag, a comment, a `LIKE`
   pattern, a regular expression, an identifier longer than 63 bytes), is a
   finding.
4. For every finding, and for every value whose safety rests on a CHECK or an
   allow-list rather than on quoting, write a test that sends a hostile value
   down that path as the request role and as an administrator, and asserts
   that nothing the value names was created, dropped or granted.
5. Generators known not to have been read by anybody in Phases 1 and 2: the
   search vector (`0160_dd_functions.sql`, `search_vector`), the queue
   triggers (`0340_queue.sql`), RACI (`0370_raci.sql`), the audit triggers
   (`0200_audit_log.sql`), `ensure_entities` (`0290_ensure_entities.sql`), the
   entity defaults and order column (`0220`, `0230`), the TypeID triggers
   (`0045_typeid.sql`) and most of `0170_dd_rename.sql`.
6. Report the findings to the maintainer at the end of Part 1, each with what
   an attacker holding which permission could do. A finding is fixed in Part
   2; none is postponed without the maintainer's word.
7. The page in `docs/` is committed with the tests, in the one commit that
   closes Part 1. Each fix of step 19 updates the row of its finding in the
   same commit as the fix.
