# Changes

## 0.5.0

First build of the rebuilt packaging. The extension is now a **thin
installer**: `CREATE EXTENSION pg_semantius` creates only the cluster roles,
the `semantius` schema and its functions, and `CALL semantius.migrate()`
installs the core schema as ordinary objects.

- `semantius.migrate()` is a **procedure**, called with `CALL` outside a
  transaction block. It commits after every migration file, takes a session
  advisory lock for the whole run (a second migrator fails at once with
  "another migration is running"), and after a failing file still runs the
  9900 files (owner hardening) before re-raising the original error. The
  files that committed before the failure stay, and the next `CALL` resumes
  there.
- **Repeatable migrations.** A `.sql` or `.jsonc` migration runs again whenever
  its text changes; a `.once.sql` / `.once.jsonc` file runs exactly once. The
  ledger key is `<app>.<full file name>` with the file's SHA-256, and
  `pending()` / `status()` follow the same rules. Entity metadata is declared in
  `.jsonc` files (the semantius-cli export format) and applied by the new
  `public.ensure_entities()`, which creates what is missing and updates what
  differs, never deleting; `public.jsonc_to_jsonb()` parses the files.
- The core migrations are renumbered `0010`, `0020`, ... and split into
  `.once.sql` (tables, indexes, seeds), repeatable `.sql` (functions, triggers,
  policies) and `.jsonc` (entity metadata). A database installed from an
  earlier 0.5.0 build has ledger rows under the old names and must be
  reinstalled.
- The RLS policies of the ten bootstrap tables are generated by the data
  dictionary (`public.create_entity_policies()`), like those of every other
  entity. `modules` rows are visible through the `select_rule`
  "admin, or the row's own `view_permission`", so `get_record_by_id()` returns
  what RLS returns. `user_bookmarks.user_id` is a computed field forced to the
  current user; a bookmark written without claims is refused (`90207`).

- Backup is a plain `pg_dump` and restore a single-pass `pg_restore`, on the
  same cluster or a fresh one. No flags, no `PGOPTIONS`, no three passes.
- `DROP EXTENSION` never causes data loss: it removes the `semantius` schema
  and its functions and nothing else, and never needs `CASCADE`.
- Custom fields added to core entities survive dump and restore.
- `schema = public` and `encoding = 'UTF8'` in the control file; no
  `requires`, so `CASCADE` can no longer install pgcrypto into the wrong
  schema. LATIN1 and SQL_ASCII databases are refused.
- New `semantius.pending()`, `semantius.version()` and `semantius.status()`.
- `_versions` gained a `checksum` column, written by both install paths and compared by both to decide what runs.
- `rbac.uid()` accepts a token that carries **no** `role` claim when its `roles`
  claim contains `authenticated`. Microsoft Entra ID is the case this exists
  for: `role` and `roles` are both in its restricted claim set, so no
  claims-mapping policy can emit `role`, and an app role named `authenticated`
  arrives as `"roles": ["authenticated"]` instead. PostgREST selects the
  database role from that same array (`jwt-role-claim-key = .roles[0]`), so both
  ends of one token read the same thing. A `role` claim holding any other value
  is still refused.
- A token from Microsoft Entra ID, recognized by its `iss` claim, identifies its
  user as `entra.<tid>.<oid>` rather than by `sub`. Entra's `sub` is pairwise:
  each app registration receives a different one for the same person, so a
  second client or a re-created registration would have produced a second
  user. An Entra token without `tid` or `oid` is refused (`90009`).
- New `public.fix_id_sequence(p_table)`: after an import that wrote explicit
  ids, moves the table's id sequence past `max(id)` so the next ordinary insert
  does not fail with 23505. Callable by holders of the entity's
  `edit_permission`; never lowers a sequence; answers `90232` (retry) when the
  table stays locked by another writer for 2 s.
- `modules.module_slug` is optional: a module saved with an empty slug gets
  one derived from `module_name` (lowercase, each run of other characters
  becoming one hyphen), on insert and on an update that clears it. A slug that
  is set is never rewritten, so renaming a module keeps its URLs.
- The field metadata of the core tables now carries the same defaults as their
  columns, so a record created through the generated UI gets the column's
  default instead of an empty value: `modules.access_scope` (`basic`, now
  required), `modules.home_page` (`/`), `modules.module_type` (`domain`),
  `modules.view_permission` (`user:read`), `roles.origin` and
  `permission_hierarchy.origin` (`user`), `entities.computed_fields` and
  `entities.validation_rules` (`[]`). Creating a module in the UI failed with
  `valid_access_scope` before.
- `get_schema()` no longer gives a reference to a text-keyed entity
  (`permissions`, `entities`) the empty string as its default. The column is
  nullable and `''` names no row, so a form that saved it failed the foreign
  key: creating a module with `manage_permission` left empty failed with
  `modules_manage_permission_fkey`.
- **Selectable key types, and 64-bit keys by default.** Every entity declares
  its key type in the new `entities.id_type`, chosen when the entity is created
  and never changed afterwards (`90233`):
  - `auto_increment` (the default): `BIGINT GENERATED BY DEFAULT AS IDENTITY`,
    id field format `int64`. Explicit ids are still accepted, and importers
    move the sequence with `fix_id_sequence()` afterwards.
  - `bigint` and `text`: supplied by the caller. The id field is `required`
    while empty and `readonly` once set (an `input_type_rule`), and
    `get_schema()` lists it in `required`.
  - `uuid`: a time-ordered UUIDv7 from the new `common.uuid_v7()` (native
    `uuidv7()` on PostgreSQL 18, a PL/pgSQL fallback on 17).
  - `typeid`: a prefixed, sortable [TypeID](https://github.com/jetify-com/typeid)
    such as `acct_01h455vb4pex5vsknk084sn02q`, stored in the new
    `common.typeid` domain (text, `COLLATE "C"`, format check
    `typeid_format`) and filled by a trigger when the insert brings none. The
    prefix is `entities.id_prefix`: TypeID grammar, unique among the prefixes
    in use, and changeable. After a change new ids take the new prefix,
    existing ids keep the old one, and an id with a former prefix can no
    longer be inserted (`90237`), so re-importing an export taken before the
    change fails for the rows it would add. A released prefix may be taken by
    another entity. `get_schema()` reports typeid keys and references to them
    as `type: string` with a TypeID `pattern`; TypeID is a key type, not a
    field format. A TypeID costs about 30 bytes per key and per referencing
    column, against 16 for a `uuid` and 8 for a `bigint`.
  - `computed` only describes the system tables whose key is a generated
    column (`fields` and the four junction tables); a new entity cannot use
    it (`90234`).

  A reference or parent column takes the type of the key it points at; for an
  entity without a table yet, the type its `id_type` gives, and for an unknown
  one `BIGINT` (was `INTEGER`). Registering an entity onto an existing table,
  or switching `managed` on for one, is refused when the table's key column
  does not match `id_type` or is missing (`90235`); `auto_increment` accepts a
  `bigint` identity or `bigserial`, not an int4 `serial`. Switching `managed`
  on is also refused when the entity already has an id field row whose format
  is not the one its `id_type` gives (`90239`): the switch never rewrites
  metadata, so switching it on and off again leaves everything as it was.
- **Record keys are immutable.** Every dictionary table, and `users`,
  `modules`, `roles` and `_apikeys`, carries a `pk_immutable` trigger: an
  update that changes the key is refused (`90236`); one that writes the
  unchanged key back passes. `entities.table_name` and
  `permissions.permission_name` stay renamable, and the generated keys of the
  junction tables still follow their key columns.
- **The core tables are 64-bit.** `users`, `modules`, `roles` and `_apikeys`
  have `BIGINT` identity keys, and every column referencing them is `BIGINT`,
  as are `audit_record_logs.user_id` and `audit_ddl_logs.user_id` (field format
  `int64`). Signatures changed accordingly: `rbac.get_user_by_external_id`,
  `rbac.upsert_user_from_jwt`, `rbac.user_id`, `rbac.user_id_or_null`,
  `audit.current_user_id` and `public.validate_api_key` return `BIGINT`;
  `rbac.get_user_permissions_by_id`, `public.generate_api_key` and
  `public.list_api_keys` take a `BIGINT` user id (the `INTEGER` versions are
  dropped). `get_schema()` casts integer defaults with `::BIGINT`.
- `get_record_by_id(p_entity_name TEXT, p_id TEXT)` replaces
  `get_record_by_id(TEXT, INTEGER)` and works for every key type; the id is
  cast to the key's own type. `get_record_by_id(p_entity TEXT, p_record_id
  BIGINT)` keeps numeric SQL callers working. The different parameter names
  keep PostgREST's overload choice unambiguous: `{p_entity_name, p_id}` and
  `{p_entity, p_record_id}` each reach one function. An id that is not a valid
  value of the key type raises `90238` for a caller who may see the entity
  (anybody else still gets `NULL`), so JsonLogic `set_record` now fails on a
  malformed id instead of loading nothing. `set_record` passes the id as text,
  with a whole JSON number normalized first (`5.0` becomes `5`).
- `user_bookmarks.entity_id` is `int64`; `0` still means "no record".
  Bookmarks can therefore point only at records of entities with numeric keys
  (`auto_increment`, `bigint`).
- Generated client types: `deno task kyselygen` types 64-bit integers as
  `number`, like PostgREST (the `Int8` string alias is gone), and the generated
  file's header asks for `pg.types.setTypeParser(20, Number)` - process-wide,
  and exact only up to 2^53. `deno task drizzlegen` builds each key from its
  `id_type` (`bigint(..., { mode: "number" }).generatedByDefaultAsIdentity()`
  for `auto_increment`) and references with the target key's type. Generated
  keys (`auto_increment`, `uuid`, `typeid`) are optional on insert in both.
- **Not an upgrade path for an earlier 0.5.0-beta1 install**: the key and
  column types above change inside `.once` files that such a database has
  already run. Reinstall it. `.jsonc` exports taken from an older instance that
  declare an id or user id field as `int32` must be edited to `int64` before
  they are imported, because a core field's format cannot change.
- Removed: the `pg_extension_config_dump` registry, the three-pass restore
  procedure and the `pg_semantius.skip_audit` workaround, none of which are
  needed once no table is an extension member.

0.5.0 is a fresh start. The earlier 0.1.0, 0.3.0 and 0.4.0 builds were
published as GitHub Releases but are treated as development snapshots: their
version history was discarded, so **there is no upgrade path from them**. An
installation on 0.3.0 or 0.4.0 cannot `ALTER EXTENSION ... UPDATE` to 0.5.0 and
cannot `DROP EXTENSION` without `CASCADE` (in those builds the core tables were
extension members). Moving to 0.5.0 means: dump the data, install 0.5.0 into a
new database, `CALL semantius.migrate()`, reload.
